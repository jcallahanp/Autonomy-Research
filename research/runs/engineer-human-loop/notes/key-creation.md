# Per-service key and token creation: automatable or UI-only

Brief: Per-service table saying whether an autonomous engineer can create the API keys, tokens or app registrations it needs by API, CLI or device flow, or whether John must click in a UI, and what each service's terms say.
Run: research/runs/engineer-human-loop/PLAN.md

Method note: pages were read with curl plus a local text stripper (Parallel fetch returned "Too Many Requests"; WebFetch paraphrases, so it was not used for quotes). Opened 2026-10-16 unless stated. Earlier work not repeated: engineer-feasibility.md Q7 and api-vs-browser.md.

## Which services can mint credentials programmatically, and what is the first human step?

### Takeaway
Three groups. (1) Parent-token minting exists: Cloudflare (create tokens via API), Vercel (REST + CLI), Supabase (PAT then Management API), Slack (config token then manifest API, but install still needs an OAuth click), Telegram (managed bots, after one human BotFather bot), Anthropic (Admin API manages keys; key creation is Console). (2) Human-only registration: GitHub PAT or App, Google OAuth client, n8n and Attio keys, Clay, Outreach, WHOOP, Withings app registration. (3) Consent per account always needs John (WHOOP, Withings, Outreach, Slack install, Google consent). Confidence: medium-high; n8n/Attio/Clay "no create-key API" is an absence claim from the docs read, not proven.

### Cited findings
- Cloudflare: a token with the right permission creates further tokens via API; the user-owned case needs a special template, account-owned needs Account API Tokens Edit. First human step is the dashboard token. — https://developers.cloudflare.com/fundamentals/api/how-to/create-via-api/, opened 2026-10-16, curl — Quote: "To create account-owned API tokens, create a token with Account > Account API Tokens > Edit. To create user-owned API tokens, use the Create additional tokens template."
- Cloudflare: the first token is made in the dashboard. — https://developers.cloudflare.com/fundamentals/api/get-started/create-token/, opened 2026-10-16, curl — Quote: "From the Cloudflare dashboard, go to My Profile > API Tokens for user tokens. For Account Tokens, go to Manage Account > API Tokens."
- Cloudflare: wrangler has a login OAuth command with remote-machine, container and no-callback-server variants. — https://developers.cloudflare.com/workers/wrangler/commands/general/, opened 2026-10-16, curl — Quote: "Use wrangler login on a remote machine Use wrangler login in a container Use wrangler login without a local callback server"
- Vercel: a token can mint tokens by REST, with an optional expiry and project. — https://vercel.com/docs/rest-api/reference/endpoints/authentication/create-an-auth-token, opened 2026-10-16, curl — Quote: "Creates and returns a new authentication token for the currently authenticated User. The bearerToken property is only provided once, in the response body"
- Vercel CLI: `vercel tokens` creates, lists and revokes tokens, optionally project-scoped; `vercel signup` creates an account from the CLI. — https://vercel.com/docs/cli/tokens, opened 2026-10-16, curl — Quote: "Tokens authenticate Vercel CLI commands and Vercel REST API requests on your behalf. They are scoped to your user account, and optionally to a single project."
- Vercel signup via CLI exists. — https://vercel.com/docs/cli/signup, opened 2026-10-16, curl — Quote: "The vercel signup command allows you to create a new Vercel account through Vercel CLI."
- Supabase: Management API needs an access token (PAT or OAuth2); PATs are generated on the account page by hand. — https://supabase.com/docs/reference/api/introduction, opened 2026-10-16, curl — Quote: "To generate or manage your personal access tokens, visit your account page."
- Supabase CLI login stores a PAT; CI skips login with an env var. — https://supabase.com/docs/reference/cli/supabase-login, opened 2026-10-16, curl — Quote: "you may skip login by specifying the SUPABASE_ACCESS_TOKEN environment variable in other commands."
- Supabase: project API keys (publishable/secret) are created in the Dashboard if absent; the docs list the Management API only as a way to read them. — https://supabase.com/docs/guides/api/api-keys, opened 2026-10-16, curl — Quote: "If your project has no publishable or secret key yet, create them first in the Settings > API Keys section of the Dashboard."
- Slack: config tokens are generated by hand on the app settings page; they drive the manifest API. — https://docs.slack.dev/authentication/tokens, opened 2026-10-16, curl — Quote: "These tokens are created on the app settings page below the list of apps. Under Your App Configuration Tokens, click Generate Token to create one."
- Slack: apps.manifest.create returns client credentials and an authorize URL, not a bot token, so install is a separate OAuth step. — https://docs.slack.dev/reference/methods/apps.manifest.create, opened 2026-10-16, curl — Quote: "\"credentials\" : { \"client_id\" : \"...\" , \"client_secret\" : \"...\" , \"verification_token\" : \"...\" , \"signing_secret\" : \"...\" } , \"oauth_authorize_url\""
- GitHub App manifest flow registers an app but redirects a person through GitHub. — https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest, opened 2026-10-16, curl — Quote: "You redirect people to GitHub to register a new GitHub App."
- GitHub PATs: the docs describe creating them in settings, plus URL-parameter pre-fill, but no creation endpoint. — https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens, opened 2026-10-16, curl — Quote: "Pre-filling fine-grained personal access token details using URL parameters"
- GitHub OAuth apps support a device flow for headless tools; `gh auth login` uses a device code. — https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps, opened 2026-10-16, curl — Quote: "device flow : Used for headless apps, such as CLI tools."
- Telegram: first bot comes from a chat with @BotFather. — https://core.telegram.org/bots/tutorial, opened 2026-10-16, curl — Quote: "Obtaining a token is as simple as contacting @BotFather , issuing the /newbot command and following the steps until you're given a new token."
- Telegram Bot API now has managed bots whose token a bot can fetch. — https://core.telegram.org/bots/api, opened 2026-10-16, curl — Quote: "Information about the bot. The bot's token can be fetched using the method getManagedBotToken ."
- Google: service-account key creation can be blocked by org policy. — https://cloud.google.com/resource-manager/docs/organization-policy/restricting-service-accounts, opened 2026-10-16, curl — Quote: "When this constraint is set, user-managed credentials cannot be created for service accounts in projects affected by the constraint."
- Google: OAuth clients are created in the console (Google Auth Platform Clients page); registration of the app comes first. — https://support.google.com/cloud/answer/15549257, opened 2026-10-16, curl — Quote: "You will be prompted to register your application to use Google Auth if you are yet to do so. This is required before creating a client."
- Google device flow supports only limited scopes. — https://developers.google.com/identity/protocols/oauth2/limited-input-device, opened 2026-10-16, curl — Quote: "This OAuth 2.0 flow supports a limited set of scopes ."
- gcloud has a no-browser login. — https://cloud.google.com/sdk/gcloud/reference/auth/login, opened 2026-10-16, curl — Quote: "command line, use the --no-browser flag."
- n8n: API keys are created in the UI; no creation endpoint is documented. — https://docs.n8n.io/connect/n8n-api/authentication.md, opened 2026-10-16, curl — Quote: "Go to **Settings** > **n8n API**. 3. Select **Create an API key**. 4. Choose a **Label** and set an **Expiration** time for the key."
- Attio: single-workspace key is generated in the Developer console; OAuth workspace-level token needs an admin. — https://docs.attio.com/rest-api/guides/authentication, opened 2026-10-16, curl — Quote: "Only workspace admins can grant a workspace-level token."
- Outreach: an app must be created, development credentials are immediate, production after review. — https://developers.outreach.io/api/oauth/, opened 2026-10-16, curl — Quote: "Development credentials are provisioned immediately and are intended to be used during application development and testing."
- WHOOP: a dashboard app comes first. — https://developer.whoop.com/docs/developing/getting-started, opened 2026-10-16, curl — Quote: "To start developing with WHOOP, you first need to create an App in the WHOOP Developer Dashboard ."
- Withings: app registered in Partner Hub; OAuth code flow. — https://developer.withings.com/developer-guide/v3/get-access/create-your-app, opened 2026-10-16, curl — Quote: "Step 1 Create your application Register in the Partner Hub to get your client credentials."
- Anthropic: API keys are generated in the Console; the Admin API list covers List, Retrieve and Update of keys, not create. — https://platform.claude.com/docs/en/manage-claude/authentication, opened 2026-10-16, curl — Quote: "API keys are static secrets that you generate in the Claude Console and send on every request as a bearer token"
- Anthropic Admin API: lists "List API Keys, Retrieve API Key (Admin API), Update API Key" under API Keys; also Service Accounts and WIF for non-interactive tokens. — https://platform.claude.com/docs/en/api/organization/api_keys/list, opened 2026-10-16, curl — Quote: "API Keys   List API Keys  Retrieve API Key (Admin API)  Update API Key"
- Clay: developers.clay.com page opened but the stripped text held no auth detail. — see Gaps.

### Contradictions
- None found. (The brief's "GitHub fine-grained PAT creation limits" has no API; both GitHub pages above show only UI creation.)

### Inferences
- (mine) Only Cloudflare, Vercel and Supabase let a parent token mint further narrower tokens by API; the engineer should receive one parent per service and mint per-task children, which makes the "first human step" the parent token. Rests on the Cloudflare, Vercel, Supabase findings.
- (mine) For Slack, a config token plus manifest API removes app-creation clicking, but the OAuth install click remains John's. Rests on the Slack findings.
- (mine) n8n, Attio, Outreach, WHOOP, Withings, GitHub and Google OAuth are one-time UI steps for John; no create-key endpoint was found in their docs.
- (mine) Anthropic: the engine itself runs on John's Max login; the engineer cannot mint an API key (Console only), so any paid API-key path is a John step; Admin API requires an organisation.

## Scope, expiry and rotation per service

### Takeaway
Narrowest scope and short expiry are available on Cloudflare, Vercel, Supabase, GitHub, Slack config tokens and n8n (expiry choice); rotation by API exists for Cloudflare (roll) and Slack (config token rotate, 12 h). OAuth services (Outreach 2 h, WHOOP refresh) need a token store (see prior notes). Confidence: medium.

### Cited findings
- Cloudflare tokens take a TTL window, and a "roll tokens" page exists. — https://developers.cloudflare.com/fundamentals/api/how-to/create-via-api/, opened 2026-10-16, curl — Quote: "you can set the time at which a token becomes active with not_before and the time when it expires with expires_on ."
- Cloudflare: safeguard the creator token. — same URL — Quote: "Make sure you safeguard the new token because it can create tokens with access to any of a user's resources."
- Slack config tokens expire in 12 hours and rotate by API with a single refresh token. — https://docs.slack.dev/reference/methods/tooling.tokens.rotate, opened 2026-10-16, curl — Quote: "Each app configuration token will expire 12 hours after it has been generated."
- Slack token rotation is irreversible (from prior note, quote in engineer-feasibility.md Q7); not re-opened here.
- GitHub PATs: automatic removal after a year unused, expiry strongly advised; infinite allowed unless policy blocks. — https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens, opened 2026-10-16, curl — Quote: "Infinite lifetimes are allowed but may be blocked by a maximum lifetime policy set by your organization or enterprise owner."
- Supabase: PATs have custom expiry and a scoped form. — https://supabase.com/docs/reference/api/introduction, opened 2026-10-16, curl — Quote: "A scoped PAT can only reach the organizations, projects, and permissions you choose when creating it."
- n8n: expiry set at creation; scopes only on Enterprise. — https://docs.n8n.io/connect/n8n-api/authentication.md, opened 2026-10-16, curl — Quote: "If you're on an Enterprise plan, choose the **Scopes** to give the key."
- Vercel token body takes expiresAt and projectId. — https://vercel.com/docs/rest-api/reference/endpoints/authentication/create-an-auth-token, opened 2026-10-16, curl — Quote: "\"name\" : \"Example Name\" , \"expiresAt\" : \"123\" , \"projectId\" : \"example_id\""
- Outreach access tokens last 7200 s and dev grants are expired periodically. — https://developers.outreach.io/api/oauth/, opened 2026-10-16, curl — Quote: "\"expires_in\" : 7200"
- WHOOP new apps start in a sandbox tier of 10 members. — https://developer.whoop.com/docs/developing/app-approval, opened 2026-10-16, curl — Quote: "Every new app starts on the Sandbox tier, which allows up to 10 WHOOP members to connect."
- Withings change dated 2026-10-12: new accounts need a membership for free-plan apps. — https://developer.withings.com/developer-guide/v3/get-access/create-your-app, opened 2026-10-16, curl — Quote: "Withings+ becomes required on the Start for Free API plan from October 12, 2026."
- Google: newer orgs enforce a default-service-account role-grant constraint by default (key-creation default not shown by this quote). — https://cloud.google.com/resource-manager/docs/organization-policy/restricting-service-accounts, opened 2026-10-16, curl — Quote: "Note : If your organization was created on or after May 3, 2024, this constraint is enforced by default."
  (The page prints that note under the default-service-account role-grant constraint; confirm it also covers key creation before relying on it. See Gaps.)
- Anthropic key types: personal, service account, legacy workspace. — https://platform.claude.com/docs/en/manage-claude/authentication, opened 2026-10-16, curl — Quote: "When you create a key, you choose its type, which determines what the key can do, where it works, and when it stops working"

### Contradictions
- None found.

### Inferences
- (mine) Child tokens should be minted per task with expiry of days and project/zone scope; the Cloudflare creator token is itself the most dangerous secret and should live outside the engineer's reach (other facet).
- (mine) Withings+ rule means John's existing account is unaffected only if created before 2026-10-12; check the account date.

### Gaps
- Default lifetimes for Cloudflare, Vercel, Attio keys: not stated in pages read.
- Attio API key scope selection UI: not opened beyond the authentication guide.
- Whether the Google org-policy default applies to John's (personal/Workspace) org: unknown; spike with `gcloud iam service-accounts keys create` in a throwaway project.

## Terms on automated signup, bots and key handling

### Takeaway
Only GitHub forbids bot-registered accounts outright while allowing a human-registered "machine account". Vercel's terms make John liable for AI tools he gives credentials. Anthropic says API-key auth, not subscription OAuth, for products built on the Agent SDK. Telegram's bot-developer terms bar sharing credentials publicly. Terms for Clay, n8n, Outreach, WHOOP, Withings, Attio (beyond one clause), Slack (credential clause) and Cloudflare account signup were not found. Confidence: low-medium.

### Cited findings
- GitHub: no bot-created accounts; machine accounts allowed if a human registers them. — https://docs.github.com/en/site-policy/github-terms/github-terms-of-service, opened 2026-10-16, curl — Quote: "You must be a human to create an Account. Accounts registered by \"bots\" or other automated methods are not permitted. We do permit machine accounts:"
- Vercel: authorising AI tools with credentials makes John responsible. — https://vercel.com/legal/terms, opened 2026-10-16, curl — Quote: "you authorize and agree to be legally bound by the actions taken on your behalf by those Third Party Tools."
- Anthropic (Claude Code legal page): subscription OAuth is for ordinary native use; products built on the Agent SDK should use API keys; no routing via Max credentials for others. — https://code.claude.com/docs/en/legal-and-compliance, opened 2026-10-16, curl — Quote: "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication through Claude Console"
- Anthropic consumer terms: no sharing credentials. — https://www.anthropic.com/legal/consumer-terms, opened 2026-10-16, curl — Quote: "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else."
- Telegram bot-developer terms: credentials may not be made public; no spam. — https://telegram.org/tos/bot-developers, opened 2026-10-16, curl — Quote: "Your TPA must not harass or spam users with unsolicited messages;"
- Cloudflare website terms only cover automated abuse-report tokens, not account signup. — https://www.cloudflare.com/website-terms/, opened 2026-10-16, curl — Quote: "If you intend to automate the process by which you submit abuse reports , you will need to request access to an abuse API token."
- Slack API terms restrict API data use by apps offered outside the org. — https://slack.com/terms-of-service/api, opened 2026-10-16, curl — Quote: "you may not: (A) use API Data to train a large language model; (B) bulk export Slack message and file data"
- Attio customer agreement limits automated decisions about people. — https://attio.com/legal/terms-and-conditions, opened 2026-10-16, curl — Quote: "Automated decision-making shall be used solely to support human decision-making"
- Supabase terms hold the customer responsible for credential use. — https://supabase.com/terms, opened 2026-10-16, curl — Quote: "the security and use of Customer's and its Authorized Users' access credentials"

### Contradictions
- None found.

### Inferences
- (mine) John running a single engineer on his own accounts is covered when John himself registers the account and apps; nothing read bans an agent calling key-mint APIs from a human-created parent token. Only GitHub explicitly bans bot-created accounts, so John creates any GitHub machine account.
- (mine) Claude Code on John's Max login for his own work fits the stated ordinary-use wording; building a service for others on that login does not.

### Gaps
- Terms for Clay, n8n, Outreach, WHOOP, Withings, Google Cloud (cloud.google.com/terms fetch gave only nav text), Cloudflare self-serve signup: no relevant clause found or page not readable.

## Recommendation
One recommendation: John creates one parent credential per service (Cloudflare Account API Tokens Edit, Vercel, Supabase PAT, Slack config token) in a single sitting, and the engineer mints narrow, short-lived children from them; John also registers every OAuth app and does every consent click (Outreach, WHOOP, Withings, Slack install, Google, GitHub). Alternatives: Playwright on dashboards for GitHub PAT pre-fill URLs; a GitHub App manifest flow. Rejected: bot-created accounts (GitHub bans them), scraping dashboards to mint keys. Spike before building: (1) Cloudflare child-token mint with narrow permissions; (2) Slack manifest create then install; (3) Google SA key creation in a throwaway project; (4) Telegram managed-bot creation; (5) Withings+ requirement on John's account; (6) n8n and Clay key-create endpoints.
