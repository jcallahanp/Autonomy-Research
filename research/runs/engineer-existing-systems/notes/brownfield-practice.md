# Brownfield practice: as-is documentation, credential inventory, sources of truth

Brief: Establish practice for documenting an existing system before re-engineering, inventorying credentials without leaking them, reconciling sources of truth and dirty data, and what an LLM agent can do reliably.
Run: research/runs/engineer-existing-systems/PLAN.md

All "opened" dates are 2026-10-16 (today), tool = WebFetch unless noted.

## Q1+Q2. As-is documentation practices, and what an LLM agent generates reliably

### Takeaway
Established practice is light: C4 context and container diagrams (C4 says these two suffice for most teams), plus Fowler-style incremental replacement and a "get it under test" first step. LLMs are good at per-unit summaries and at drafting boxes-and-arrows when fed static-analysis structure, but plain repo-wiki tools (DeepWiki class) score about 64-73% on a documentation benchmark and are reported to hallucinate plausibly; every generated claim needs a file/line citation and a check. Confidence: medium (no controlled study of "diagram then better decisions"; benchmarks are by tool authors).

### Cited findings
- C4 says the two upper levels are usually enough — https://c4model.com/diagrams, opened 2026-10-16, WebFetch — Quote: "you don’t need to use all 4 levels of diagram"
- C4 was designed for retrospective documentation and lists risk identification as a benefit — https://c4model.com/introduction, opened 2026-10-16, WebFetch — Quote: "both during up-front design sessions and when retrospectively documenting an existing codebase"
- C4 container = application or data store (so Postgres, n8n, Attio, Clay each map to a container or external system) — https://c4model.com/diagrams/container (seen in search excerpt only, not opened; not relied on). See Gaps.
- Fowler: gradual replacement preferred over big-bang rewrite — https://martinfowler.com/bliki/StranglerFigApplication.html, opened 2026-10-16 — Quote: "we've seen this simple-sounding plan go down in flames most of the time."
- Fowler on risk of small increments — same URL — Quote: "Since these components are small, there isn't so much risk involved when we introduce the new software."
- Seams and tests come first when changing legacy code — https://martinfowler.com/bliki/LegacySeam.html, opened 2026-10-16 — Quote: "getting a legacy system under test, as that is often the key to being able to work with it in a sane way"
- LLM per-unit documentation of legacy code (MUMPS, assembly) judged largely hallucination-free by humans; automated metrics did not predict quality (2025) — https://arxiv.org/pdf/2411.14971 (search excerpt only; abstract also at https://www.computer.org/csdl/proceedings-article/llm4code/2025/261500a177/27uepXghRjW, not opened). Moved to Gaps, not relied on.
- Whole-repo LLM summarisation has local-scope bias and hallucinated identifiers; adding dependency context raised F1 (2026) — https://arxiv.org/html/2601.13007v1, opened 2026-10-16 — Quote: "they may omit functions, misstate control flow, or hallucinate identifiers when asked to summarize whole files or packages"
- Same paper: dependency modelling matters; F1 ArchAgent 0.966 vs DeepWiki 0.860 (authors' own tool, 8 repos) — https://arxiv.org/html/2601.13007v1, opened 2026-10-16 — Quote: "dependency modeling is non-redundant for architectural recovery."
- CodeWiki benchmark (ACL Findings 2026): DeepWiki 64.06% vs CodeWiki 68.79% with proprietary models; i.e. the best repo-wiki systems are mid-60s to high-60s percent — https://arxiv.org/abs/2510.24428, opened 2026-10-16 — Quote: "outperforming the closed-source DeepWiki baseline (64.06%) by 4.73%"
- Practitioner reports of DeepWiki errors (Aug 2025, anecdotal) — https://news.ycombinator.com/item?id=45002092, opened 2026-10-16 — Quote: "the slop was generated by DeepWiki. It was very incorrect"
- Industry mainframe case (Thoughtworks): earlier naive genAI output was poor; AST-assisted pipeline cut reverse-engineering time by two-thirds — https://www.thoughtworks.com/en-br/clients/mainframe-modernization-ai, opened 2026-10-16 — Quote: "technical SMEs found they were only 60% accurate."
- Same page, vendor result — Quote: "Reverse engineering time was reduced by two-thirds — from six weeks to around two weeks for each 10,000-line module."
- CIAO study (22 developers, 2026): LLM architecture docs rated broadly accurate but weak on diagrams, high-level context, deployment — https://arxiv.org/abs/2604.08293, opened 2026-10-16 — Quote: "diagram quality, high-level context modeling, and deployment views."

### Contradictions
- Per-function legacy comments rated largely hallucination-free (arXiv 2411.14971, search excerpt) versus repo-level wikis rated mid-60s percent and called "very incorrect" (CodeWiki ACL; HN thread). Likely explained by granularity (line/unit vs whole-system); not settled by one study.
- Thoughtworks vendor claim of two-thirds time saving versus the same page's earlier 60% SME-judged accuracy of raw genAI: the gain depends on the AST-assisted pipeline plus SME review, not on the LLM alone.

### Inferences
- (mine) Reliable agent work: inventory by deterministic extraction (list workflows, tables, env var names, imports), with the LLM only labelling and summarising each unit; each claim stored with file:line or API-response evidence. Unreliable: inferred intent, "why", deployment and runtime topology, and whole-repo narrative. Rests on ArchAgent, CodeWiki, CIAO, Thoughtworks findings above.
- (mine) Highest-value human checkpoint is the context-level diagram and the "what is the source of truth for X" list, because those are where CIAO found weakness.

### Gaps
- No controlled evidence that a given as-is format leads to better re-engineering decisions (see Q4).
- https://arxiv.org/pdf/2411.14971 and the C4 container page were seen only as search excerpts, not opened; PDF of 2604.08293 would not parse (used abstract page instead).
- Thoughtworks Technology Radar vol 33 (Nov 2025) seen in a snippet only; not opened.

## Q3. Inventorying credentials without leaking secrets

### Takeaway
Do it in two layers: (1) hard gates so the agent cannot read secret-bearing files or values (permission deny rules plus sandbox), and (2) inventory by metadata: scanners run with redaction and a file report that the agent reads only in redacted form, and n8n's credentials API, which does not return secret values to API clients. Record "name, type, where used, owner, last rotated", never the value. Confidence: medium-high; deny-rule enforcement has had bugs, so spike it.

### Cited findings
- Claude Code deny rules exist for secret-file reads — https://code.claude.com/docs/en/settings-reference (search excerpt only); confirmed on the opened example page: https://code.claude.com/docs/en/settings-example, opened 2026-10-16 — Quote: "`Read(./.env)` on its own stops the file tools and commands that name the file, such as `cat .env`, but not [`grep -r` run over the directory]"
- Same page: the sandbox closes that gap — Quote: "the `sandbox` block in this file closes that gap, because the sandbox [adds your `Read` deny paths] to what every sandboxed command can't read."
- Deny rules were once reported as not enforced (Feb 2026, closed as duplicate of #6699) — https://github.com/anthropics/claude-code/issues/24846, opened 2026-10-16 — Quote: "The `Read` tool call succeeds despite matching the deny pattern. The full contents of `.env.local` ... are read and displayed."
- Gitleaks can redact secrets in output and writes json/csv/sarif reports — https://github.com/gitleaks/gitleaks, opened 2026-10-16 — Quote: "redact secrets from logs and stdout. To redact only parts of the secret just apply a percent value from 0..100."
- Gitleaks directory scan and report path — same URL — Quote: "gitleaks dir -v path_to_directory_or_file"
- Gitleaks baseline = any previous report, so existing findings can be accepted and only new ones shown — snippet of README only; see Gaps.
- TruffleHog scans a filesystem and can disable verification — https://github.com/trufflesecurity/trufflehog, opened 2026-10-16 — Quote: "Don't verify the results."
- TruffleHog default verification checks liveness against provider APIs — same URL — Quote: "verified: Credential confirmed as valid and active by API testing"
- n8n public API has scopes to list credentials, and a security-audit scope — https://docs.n8n.io/connect/n8n-api/authentication, opened 2026-10-16 — Quote: "`credential:list` | List credentials."
- n8n API read returns schema, not value — same URL — Quote: "`credential:read` | Retrieve a credential and its data schema."
- n8n audit — same URL — Quote: "`securityAudit:generate` | Generate a security audit report for the instance."
- n8n's own API design rule: secrets are write-only over the public API — https://github.com/n8n-io/n8n/blob/master/.agents/skills/public-api/reference.md, opened 2026-10-16 — Quote: "GET never returns the real secret; it returns that sentinel (or omits the field)."

### Contradictions
- Docs say `Read(./.env)` deny blocks file reads (settings-example), while issue #24846 reports it was not enforced; the docs also say it misses `grep -r`. Settle by a spike on the pinned Claude Code version.

### Inferences
- (mine) Use `trufflehog --no-verification` (or gitleaks) so that discovered secrets are not sent to third-party APIs for liveness checks; verification is a separate, human-approved step. Rests on the TruffleHog quotes.
- (mine) For a record of "which key exists and where": store {secret type, rule id, file, line, commit, fingerprint or hash, n8n credential id and name, workflows using it}. Never store Match or Secret fields; gitleaks `--redact` (100% default for logs, but check the report file separately: baseline.json in its testdata shows masked Secret fields). Verify before relying on it.
- (mine) Safest agent posture: the agent receives only the redacted scanner report and API metadata; secrets used by its own tools live in a proxy or env outside its context (the repo registry notes the cloud network-secrets feature does this).
- (mine) Env-file convention: commit `.env.example` with names only; the inventory lists names, not values.

### Gaps
- Not verified: whether a gitleaks JSON report with `--redact` masks the Secret and Match fields in the report file itself (the README says "from logs and stdout"). Must be spiked.
- n8n GET /credentials list response fields (id, name, type) not confirmed from an opened page; the handler file fetch returned 404 at raw.githubusercontent.com. n8n credential-to-workflow usage mapping would come from workflow JSON (nodes carry credential id and name), unconfirmed here.
- detect-secrets baseline (hashed secrets) seen in search excerpt only; cloud IAM listings (AWS/GCP/Supabase/Vercel key listing) not researched.
- Trufflehog redaction semantic: README text did not explain it.

## Q4. Reconciling sources of truth and dirty data (Attio, Postgres, Clay)

### Takeaway
Practice: pick one system of record per field, make enrichment tools write only through a matching key with a lookup-first rule, find duplicates with explicit weighted match rules, merge only with human approval or high-confidence gating, and keep an audit log. Attio's native merge is pairwise and not documented as reversible; the add-on tools add reversibility. Confidence: medium.

### Cited findings
- Clay's own guidance: the CRM stays the source of truth, enrichment runs alongside — https://www.clay.com/guides/crm-enrichment-guide (2026-04-10), opened 2026-10-16 — Quote: "Salesforce or HubSpot stays the source of truth"
- Clay-to-Attio: look up first, upsert on a unique matching attribute — https://university.clay.com/docs/attio-integration, opened 2026-10-16 — Quote: "Use upsert when uncertain" (doc also: "Start with lookup" to check for duplicates before creating)
- Clay Update record can overwrite multiselect values — same URL — Quote: "Overwrite multiselect values," which "replaces existing values."
- Clay: verify before overwrite (conditional run) — https://www.clay.com/guides/crm-enrichment-guide, opened 2026-10-16 — Quote: "the write only fires when the new value actually changed and cleared its verification status."
- Attio native merge combines related data; right-hand record wins conflicts; no stated undo — https://attio.com/help/reference/managing-your-data/records/merge-and-delete-records, opened 2026-10-16 — Quote: "once a record is deleted, it cannot be recovered by you or your team."
- Attio Dedupe (third-party app listing): weighted per-attribute match rules, confidence gating, audit log, 30-day reversibility — https://attio.com/apps/dedupe, opened 2026-10-16 — Quote: "automation is confidence-gated (auto-merge above your threshold, ambiguous clusters queued for review)"
- Same page — Quote: "every merge is logged and reversible for 30 days."
- Existing Claude skill for Attio dedupe uses detect, report, approve, merge, and notes API limits (2026, unvetted third-party repo) — https://github.com/gmaramigin/attio-dedup-audit-skill, opened 2026-10-16 — Quote: "The Attio API does not have a delete endpoint."
- Same repo — Quote: "Nothing happens without you saying "go.""
- Salesforce pattern: matching rules decide what is a duplicate, duplicate rules decide what happens, duplicate jobs find existing ones (page dated 2026-09-25 in search metadata) — https://help.salesforce.com/s/articleView?language=en_US&id=sales.managing_duplicates_overview.htm (search excerpt only, not opened). Moved to Gaps.

### Contradictions
- Attio's help page does not document merge undo, while the Dedupe app listing claims 30-day reversibility (and a second app, Deduptio, claims 24 hours, seen in snippet only). Treat reversibility as a property of the add-on, not of Attio; verify in a sandbox workspace.

### Inferences
- (mine) A one-time reconciliation table per entity (person, company, deal): field, Attio value, Postgres value, Clay value, chosen system of record, rule. Default rule: system of record wins; enrichment fills blanks only; overwrite only when verified and changed. This follows Clay's "source of truth" and "verify before overwrite" statements.
- (mine) Agent role: read-only diff and report; merges and deletes only after John approves a cluster, and export a snapshot of Attio before any bulk change since delete is unrecoverable.
- (mine) Third-party Attio dedupe apps are paid or unvetted; start with a free scripted match-and-report against a Postgres export (email/domain normalised), and only buy if the volume justifies it.

### Gaps
- Salesforce/HubSpot dedupe docs not opened; Attio's native duplicate-detection scope (domain for companies, email for people) from a snippet only.
- No evidence found on Postgres-as-system-of-record vs CRM reconciliation patterns specifically; no price check on dedupe apps.

## Q5. What the as-is deliverable should look like, and evidence that it helps

### Takeaway
Practitioner consensus supports a small set: C4 context + container map (with data stores and external systems), a credential and integration inventory, a source-of-truth table, and a keep/replace/remove table with a risk list, tied to incremental replacement. I found no study showing the format improves re-engineering decisions; the support is design rationale (C4 lists onboarding, reviews, risk identification; Fowler argues for small risk-limited steps). Confidence: low-medium on the evidence, medium on the format.

### Cited findings
- C4 benefits include risk identification — https://c4model.com/introduction, opened 2026-10-16 — Quote: "risk identification (e.g. risk-storming)"
- Gradual strangler approach limits risk and delivers earlier value — https://martinfowler.com/bliki/StranglerFigApplication.html, opened 2026-10-16 — Quote: "the reduced risk and earlier value from the gradual approach outweigh its costs"
- LLM-assisted reverse engineering reduced documentation lead time (vendor case) — https://www.thoughtworks.com/en-br/clients/mainframe-modernization-ai, opened 2026-10-16 — Quote: "from six weeks to around two weeks for each 10,000-line module."

### Contradictions
- None found.

### Inferences
- (mine) Deliverable, in order: (1) context+container Mermaid diagram; (2) system-of-record table; (3) credential/permission inventory (names, scopes, locations, no values); (4) data-quality findings with counts; (5) gap list ("unknown, ask John"); (6) risk list; (7) keep/replace/remove table with evidence links. Each row cites file:line, API call, or "stated by John".
- (mine) Mark each statement as observed, inferred, or asserted by John; this guards against plausible-but-wrong prose, per the DeepWiki reports.

### Gaps
- No source found for "keep, replace, remove" tables as a named practice with outcome data; Thoughtworks "6R"-style disposition models not researched. No evidence that diagram-first improves decisions.

## Recommendation, alternatives, rejects, spikes (for synthesizer)
- Recommendation: agent-built as-is pack from deterministic extraction (n8n API workflow JSON and credential metadata, Postgres schema, Attio/Clay object and field lists, repo scan), rendered as C4 context+container Mermaid plus the tables above; scanner runs through gitleaks (redacted) or trufflehog `--no-verification` behind deny rules and sandbox; John reviews the context diagram and the system-of-record table.
- Alternatives: DeepWiki-style wiki as a navigation aid only; Structurizr/LikeC4 style diagram-as-code (not researched); paid Attio dedupe app.
- Rejected: using a generated wiki as the as-is truth (mid-60s benchmark scores, anecdotal hallucination); TruffleHog with verification on by default (sends found secrets to providers); agent-driven bulk merge without approval.
- Spike before building: (a) deny rules + sandbox keep `.env` and n8n credential data out of context on the pinned Claude Code version; (b) gitleaks `--redact` in JSON report content; (c) n8n credentials list response and workflow-JSON credential references; (d) Attio merge undo in a sandbox workspace and API limits; (e) agent-extracted diagram vs John's own knowledge on one real system.
