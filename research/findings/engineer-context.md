# Engineer context: context, memory, task tracking, loops and model tiers for an autonomous Claude Code engineer

**Summary.** The evidence, all opened 2026-10-16, says the engineer should keep its state in repo files and its sessions short, and should trust hooks and scripts rather than its own memory or its own "done". Claude Code gives the carriers: "Each Claude Code session begins with a fresh context window" (https://code.claude.com/docs/en/memory); after compaction only root CLAUDE.md, auto memory and the plan-mode plan come back from disk while "Context that hooks added earlier | Summarized with the rest of the conversation" (https://code.claude.com/docs/en/context-window), and the documented fix is "a `SessionStart` hook with a `compact` matcher to re-inject critical context after every compaction" (https://code.claude.com/docs/en/hooks-guide). CLAUDE.md rules are advisory: "Claude treats them as context, not enforced configuration" (https://code.claude.com/docs/en/memory), so a forgotten document update is prevented only by a hook; an Anthropic maintainer closed the request for an evidence gate with "There is a supported way to do this today: a `Stop` hook." (https://github.com/anthropics/claude-code/issues/75720). Context rot is real but conditional: in a 2026 coding-agent study "a 10,991-character clean context passes 8/10 runs, whereas two 299,140-character contexts ... each pass 3/10" and "38 of 44 failed runs nevertheless end with a success, safe, or completion claim", while "A detailed external checklist passes 10/10 runs, compared with 5/10 for a generic self-check" (https://arxiv.org/html/2607.17937v2); one agentic study finds "Degradation is driven by step count rather than context length" (https://arxiv.org/pdf/2609.01660v1), and no study measures Claude Code on a multi-hour coding task. Of the named tools, Superpowers is a process layer whose own skill says "Conversation memory does not survive compaction." and answers with a git-ignored ledger (https://github.com/obra/superpowers skills/subagent-driven-development/SKILL.md:131 (commit bb92a77)); Beads is a Dolt issue graph that "replaces messy markdown plans with a dependency-aware graph" (https://github.com/steveyegge/beads README.md:15 (commit d274841)) with an ops surface that includes "the 2026-08-11 fleet-wide data loss." (docs/recovery/init-safety.md:344); and the official Ralph plugin's "Stop hook feeds the SAME prompt back" with "`--max-iterations <n>` - Stop after N iterations (default: unlimited)" (https://github.com/anthropics/claude-code plugins/ralph-wiggum/README.md:23,60 (commit 03b5892)), which produced "One `/ralph-loop` ran **6,239 iterations over ~11.7 hours** before noticed." (https://github.com/anthropics/claude-plugins-official/issues/1699). Every Claude Code loop bound defaults to none ("No limit by default." for `--max-turns`, https://code.claude.com/docs/en/cli-reference), so an outer supervisor must own turns, budget, wall clock, attempts per task and a git-diff circuit breaker (thresholds 3 and 5 from https://raw.githubusercontent.com/frankbria/ralph-claude-code/main/lib/circuit_breaker.sh). On model tiers, Anthropic's guidance is "Reserve Opus for complex architectural decisions or multi-step reasoning." and "For simple subagent tasks, specify `model: haiku`" (https://code.claude.com/docs/en/costs); Haiku 5.5 "pairs well with Opus 5.5 and Sonnet 5.5 as a subagent on coding work" but "Sonnet 5.5 and Opus 5.5 remain better choices for complex agentic coding tasks" (https://www.anthropic.com/claude-haiku-5-5); a separate evaluator "is worth the cost when the task sits beyond what the current model does reliably solo" (https://www.anthropic.com/engineering/harness-design-long-running-apps). The combined protocol (Q7) is: native Claude Code memory stack plus Superpowers brainstorm/plan/ledger, repo-resident `tasks.json` + `PROGRESS.md` + a doc-dependents manifest, a `SessionStart` compact/resume hook, a Stop/TaskCompleted command hook that runs the evidence command and the doc-manifest check, one fresh `claude -p` session per task under a supervisor with hard caps and a `RUN_STATUS.json`, Opus/Fable-class for planning and debugging, Sonnet-class for implementation and review, Haiku 5.5 only for narrow checkable roles until a paired test on John's own tasks shows no loss.

## Questions and answers

### Q1. What do Superpowers, Beads, Ralph and Claude Code's native features each contribute to context, memory and task tracking, and what are their documented failure modes?

**Confidence: high** for the skills, READMEs and official docs (read in clones or opened pages); **medium** for the issue trackers (list pages only, bodies not opened).

**Claude Code native.** The platform supplies the carriers everything else attaches to. "Each Claude Code session begins with a fresh context window." (https://code.claude.com/docs/en/memory). Instruction memory is CLAUDE.md, with "target under 200 lines per CLAUDE.md file." (same page); learned memory is auto memory, where "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation." (same page). Both are advisory: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." (same page). Compaction re-injects root CLAUDE.md, auto memory and the plan-mode plan, but "Context that hooks added earlier | Summarized with the rest of the conversation" and path-scoped rules and nested CLAUDE.md are lost because "compaction summarizes them away with everything else." (https://code.claude.com/docs/en/context-window); Claude Code "re-reads up to five of the files Claude has read or edited in the session" (same page). The compaction summary "keeps: your requests and intent, key technical concepts, files examined or modified with important code snippets, errors and how they were fixed, pending tasks, and current work." (same page), so pending tasks survive only as prose. The documented re-injection point is "Use a `SessionStart` hook with a `compact` matcher to re-inject critical context after every compaction." (https://code.claude.com/docs/en/hooks-guide); SessionStart matchers also include resume: "`resume` is \"`--resume`, `--continue`, or `/resume`\"" (https://code.claude.com/docs/en/hooks). The task list is per session unless shared: "To share a task list across sessions, set `CLAUDE_CODE_TASK_LIST_ID` to use a named directory in `~/.claude/tasks/`" (https://code.claude.com/docs/en/interactive-mode), and the Task tools are "available by default only on Opus 4.7, Sonnet 4.6, Haiku 4.5, and earlier models" (https://code.claude.com/docs/en/tools-reference), which is why the earlier findings file warns "On newer models, Claude keeps track of multi-step work without a written checklist" (/home/user/Autonomy-Research/research/findings/context-management.md:19). Subagents: "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions." and "The `memory` field gives the subagent a persistent directory that survives across conversations." (https://code.claude.com/docs/en/sub-agents). Plan mode "tells Claude to research and propose changes without making them." but under bypass permissions "Claude Code also doesn't enforce plan mode's blocks." (https://code.claude.com/docs/en/permission-modes). Resume restores history, model and permission mode, but "Not every configuration flag from the original launch is restored." (https://code.claude.com/docs/en/sessions); `-p` sessions are left "out of the session picker and out of `claude --continue`." (same page); "A tool that was still running when the previous process ended, for example in a crash, doesn't finish or run again when you resume." (same page). Native Claude Code also bounds a misbehaving Stop hook: "Claude Code overrides a Stop hook after it blocks eight times in a row with no tool call from Claude in between." (https://code.claude.com/docs/en/hooks-guide). What native does not give (worker inference, named-tools note): a dependency graph, a durable cross-machine ledger, or an iteration loop with verification.

**Superpowers (v7.0.0, commit bb92a77).** A process layer, not a memory store. Its state is files: a spec committed after a hard human gate, "Nothing gets built until your human partner approves the full" (https://github.com/obra/superpowers skills/brainstorming/SKILL.md:180 (commit bb92a77)); a plan with two executors, "A fresh subagent implements each task and a fresh reviewer checks it before the next one starts" (skills/writing-plans/SKILL.md:191); subagents that "should never inherit your session's context or history" (skills/subagent-driven-development/SKILL.md:10); and a ledger, because "Conversation memory does not survive compaction." (skills/subagent-driven-development/SKILL.md:131) and "after compaction, trust the ledger and `git log` over your own" (skills/executing-plans/SKILL.md:135). Inline execution stops only in four cases, "Four things stop you, and only these: an irreversible or destructive" (skills/executing-plans/SKILL.md:39), and the skill admits that on a long plan "its later tasks would run on a compacted context." (skills/executing-plans/SKILL.md:62). A SessionStart hook re-injects the bootstrap: "\"matcher\": \"startup|clear|compact\"," (hooks/hooks.json:5). The worktree skill is isolation only: "Ensure work happens in an isolated workspace." (skills/using-git-worktrees/SKILL.md:8). Open issues on the list page (titles only, Oct 2026): #2481 fix rounds exceed the compaction re-attach cut; #2493 plan constraints do not reach the implementer ("never reach the implementer"); #2510 agent changed an approved plan despite CLAUDE.md saying wait; #2506 design approval used to skip worktree consent (https://github.com/obra/superpowers/issues?q=is%3Aissue+compaction+OR+context+OR+skipped). Worker inference: its human burden is front-loaded (approve design, pick executor, consent to merge/push); no forgotten-document-update guard exists in the skills read; the ledger covers task progress only.

**Beads (commit d274841).** A Dolt-backed issue graph read through the `bd` CLI: "It replaces messy markdown plans with a dependency-aware graph, allowing agents to handle long-horizon tasks without losing context." (https://github.com/steveyegge/beads README.md:15 (commit d274841)); the agent block says "Do not use markdown TODO lists for task tracking." (README.md:57); `bd remember` will "Store project memory that `bd prime` injects later." (README.md:79); "Hash-based IDs (`bd-a1b2`) prevent merge collisions in multi-agent/multi-branch workflows." (README.md:62); and "Semantic \"memory decay\" summarizes old closed tasks to save context window." (README.md:65). Its Claude Code integration relies on SessionStart: "No `PreCompact` hook is needed - SessionStart fires again after compaction." (docs/integrations/claude-code.md:49). Its own comparison says GitHub Issues has "No built-in \"ready\" concept; requires custom GraphQL plus a sync service" (docs/reference/faq.md:20) while conceding "GitHub Issues and Jira excel for human teams working in a web UI with cross-repo dashboards and integrations." (docs/reference/faq.md:25). Failure modes are operational: "the 2026-08-11 fleet-wide data loss." (docs/recovery/init-safety.md:344), and on the issue list page (25 of 446 shown) stale derived state, autosync push failures, a 503 on a proxied server, and "Default actor falls back to git user.name for non-interactive callers, so agent changes are recorded as the repo owner" (https://github.com/steveyegge/beads/issues?q=is%3Aissue+agent+ignores+OR+forgets+OR+stale). Worker inference: Beads adds what native lacks (dependencies, ready queue, multi-agent claim, git-synced history) at the cost of a Dolt server and an immature ops surface; because the README block is "context, not enforced", a SessionStart hook running `bd prime` is the stronger wiring.

**Ralph Wiggum loop.** "Ralph is a technique. In its purest form, Ralph is a Bash loop." (https://ghuntley.com/ralph/) with "One item per loop. I need to repeat myself here—one item per loop." (same page) and "The name of the game is that you only have approximately 170k of context window to work with." (same page). The official plugin runs it in-session: "Stop hook feeds the SAME prompt back" (https://github.com/anthropics/claude-code plugins/ralph-wiggum/README.md:23 (commit 03b5892)), "`--max-iterations <n>` - Stop after N iterations (default: unlimited)" (README.md:60), "Always rely on `--max-iterations` as your primary safety mechanism." (README.md:134), the hook prints "Ralph loop: Max iterations ($MAX_ITERATIONS) reached." at the cap (hooks/stop-hook.sh:52), and the README excludes "Tasks requiring human judgment or design decisions" (README.md:160). Documented failures: "Claude attempted this task 1,966 times" (https://dev.to/sean8/i-accidentally-made-claude-ask-itself-the-same-question-1966-times-1c5h); "One `/ralph-loop` ran **6,239 iterations over ~11.7 hours** before noticed." and "No-op detection — there is none. Iteration N+1's assistant output can be byte-identical to iteration N's; the loop continues regardless." (https://github.com/anthropics/claude-plugins-official/issues/1699); a Docker restart-on-failure setup that produced "67 workspace branches" where "every single one was empty." (https://www.adrosenfeld.com/blog/2026-02-16-when-your-agent-burns-71-percent-of-your-tokens/), fixed by changing "Default `RALPH_MAX_ITERATIONS` from `0` (unlimited) to `5`." (same page); and the secondary podcast notes "It stops when you hit Ctrl-C. That is it." and "When it says it's done, it's not really done." (https://gist.github.com/accelas/762f7e96e8310b43986581aed73e31be). Worker inference: the plugin's in-session loop keeps one growing context, so the fresh-context benefit of the bash form is lost; safe use is an external `claude -p` loop with a hard cap, one task per iteration from a task file, script-checked completion and branch isolation.

**Comparable systems (one idea each).** Cline's Memory Bank exists because "my memory resets completely between sessions" and splits files by role, "Current focus, recent changes, next steps (updates most frequently)" (https://docs.cline.bot/features/memory-bank); Aider's repo map is a token-budgeted ranked map, "The token budget is influenced by the `--map-tokens` switch, which defaults to 1k tokens." (https://aider.chat/docs/repomap.html); Devin's Knowledge is trigger-recalled, "Devin will retrieve a Knowledge item when its current work is related to the specified triggers." (https://docs.devin.ai/product-guides/knowledge); OpenHands skills "activate when a user message contains configured terms." (https://docs.openhands.dev/openhands/usage/microagents/microagents-overview). Worker inference: all are files-on-disk plus selective loading, which CLAUDE.md, auto memory and skills already do; the transferable ideas are Cline's activeContext/progress split and Devin's trigger descriptions.

**Overlap map (worker inference, named-tools note).** Superpowers' ledger = native task list + plan file + git; Superpowers' SessionStart bootstrap = native SessionStart hook; Beads' `bd remember`/`prime` = auto memory + CLAUDE.md; Beads' graph/claim = no native equivalent; Ralph = Stop hook plus loop, and native supplies only the eight-block cap, which tool calls reset, so it does not bound Ralph.

**Contradictions.** (1) The task brief assumed subagents cannot spawn subagents; the sub-agents page, as summarised by the fetch model, says nesting is allowed by default up to three layers (https://code.claude.com/docs/en/sub-agents), and the earlier findings record "nesting three layers by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`)" (/home/user/Autonomy-Research/research/findings/architecture.md:55). The evidence favours the docs; the exact wording is a spike item. (2) The plugin README's cost headline "One $50k contract completed for $297 in API costs" (plugins/ralph-wiggum/README.md:169 (commit 03b5892)) against the 1,966-iteration incident with zero output (https://dev.to/sean8/i-accidentally-made-claude-ask-itself-the-same-question-1966-times-1c5h): different setups, not a factual conflict, but the headline is anecdotal.

### Q2. What is the evidence on context rot, and which mitigations have measured effects?

**Confidence: medium-high** that rot exists and that external checklists beat self-checks; **low** on any threshold for current Claude models (no study measures Claude Code on multi-hour coding).

**Degradation with length.** Single-call studies: "performance is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle" (https://arxiv.org/abs/2307.03172); "While these models all claim context sizes of 32K tokens or greater, only half of them can maintain satisfactory performance at the length of 32K." (https://arxiv.org/abs/2404.06654); "At 32K, for instance, 11 models drop below 50% of their strong short-length baselines." (https://arxiv.org/abs/2502.05167); and across 18 models "even under these minimal conditions, model performance degrades as input length increases, often in surprising and non-uniform ways." (https://research.trychroma.com/context-rot). Anthropic treats it as a design premise, "These factors create a performance gradient rather than a hard cliff: models remain highly capable at longer contexts but may show reduced precision" (https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), and its Claude Code guidance says "Claude's context window fills up fast, and performance degrades as it fills." (https://code.claude.com/docs/en/best-practices).

**Agentic and coding studies (2026).** CertiK, Codex with gpt-5.4-mini: "a 10,991-character clean context passes 8/10 runs, whereas two 299,140-character contexts—one relevant and one irrelevant—each pass 3/10." (https://arxiv.org/html/2607.17937v2); failure is sparse and masked, "In a broader mixed inventory, 38 of 44 failed runs nevertheless end with a success, safe, or completion claim." (same URL); and there is no onset, "Scale pilots do not identify a stable onset: a failure appears at 90K once but disappears on replay, while 299K remains risky." (same URL); the frame is "Context rot should therefore be treated as a conditional reliability distribution over model, task, scaffold, and context—not a single window threshold" (same URL). The only Claude 4.6-era datum is a monitoring task: "Opus 4.6 (with thinking)'s recall drops from 99.7% when such an attack is inserted in a 100K transcript to 69% when the same attack is inserted in an 800K transcript." and "We observe that in the middle is the hardest point for models to identify the attack and that this effect is stronger on the non-thinking model." (https://arxiv.org/pdf/2605.12366). A nine-model agentic study (no Claude confirmed) finds "Degradation is driven by step count rather than context length: bounding the context window steepens decay rather than easing it (logit slope -0.69 vs. -0.44)" (https://arxiv.org/pdf/2609.01660v1). The only agent-role models in these 2026 coding studies are non-Claude: "The main repeated experiment uses Codex with gpt-5.4-mini" (https://arxiv.org/html/2607.17937v2).

**Mitigations with measurements.** An external checklist beat self-check: "A detailed external checklist passes 10/10 runs, compared with 5/10 for a generic self-check (p=0.0325)" (https://arxiv.org/html/2607.17937v2). Delegation does not make a worker durable: "after a cleanly verified 2.4M-character load and native compaction, the worker reports losing an opaque contract and produces an exact artifact only by reading prohibited recovery material." with the caveat "This single mechanism run is not a threshold estimate" (same URL); smaller evidence sets help conditionally, "Small scaffold probes suggest that coding agents can also help by selecting a smaller evidence set, but they neither eliminate rot" (same URL). What the earlier findings establish from documentation: "detailed instructions from early in the conversation may be lost" (/home/user/Autonomy-Research/research/findings/context-management.md:11); "Invoked skill bodies: Re-injected, capped at 5,000 tokens per skill and 25,000 tokens total; oldest dropped first" (context-management.md:11); auto-compaction stops when "a file or tool output immediately refilled the context window several times in a row" (context-management.md:11); PreCompact's stdout "goes to the debug log\", so it cannot add instructions" (context-management.md:21); "A clean session with a better prompt almost always outperforms a long session with accumulated corrections" (context-management.md:49); "After compaction, trust the ledger and git log over your own recollection" (context-management.md:102); "Progress ledger file written after every subagent returns, read first after any compaction" (context-management.md:112); and its own stated limit, "the degradation shape for current models in the 200K-1M range is unknown, so the \"lead holds little\" rule rests on the general finding" (context-management.md:145). For unattended runs Anthropic recommends that "a verification subagent or a dynamic workflow that checks its own findings has a fresh model try to refute the result" (https://code.claude.com/docs/en/best-practices).

**Worker inferences (context-rot note).** For an engineer running hours, the dominant risk is silent omission of earlier obligations plus an unwarranted "done" (CertiK's 38 of 44), so external verification beats self-check. Because onset is unstable and one study ties decay to steps, a session-age or step-count rotation rule is better grounded than a token threshold alone. Compaction should be treated as lossy; decisions must live in files. What transfers from the research agent: ledger-plus-git recovery, Compact Instructions, SessionStart `compact` re-injection, output-truncating hooks, fresh subagent per task with a report-file contract, no mid-run model or effort change. What is missing for an engineer: a session rotation rule, an acceptance-criteria file re-read at each task start, and a check that compaction did not lose a decision.

**Contradictions.** (1) Step count vs length: "Degradation is driven by step count rather than context length" (https://arxiv.org/pdf/2609.01660v1) against CertiK's 299K-character contexts hurting "relevant and one irrelevant—each" alike (https://arxiv.org/html/2607.17937v2) and the Fellows' recall falling with prepended tokens (https://arxiv.org/pdf/2605.12366). Different tasks, none on a Claude Code session; unresolved. Both sides agree the lever is fewer steps and less carried state rather than a hard window cap, since the step-count study reports bounding context made decay steeper. (2) Subagent isolation: Anthropic's "only the relevant summary returns" line and the research-agent findings (/home/user/Autonomy-Research/research/findings/context-management.md:49) favour isolation, while CertiK finds a fresh worker is not durable across compaction (https://arxiv.org/html/2607.17937v2). Unresolved; no study of Claude subagents on coding.

### Q3. What subagent architecture fits a long-running coding engineer, and which model tier handles which role?

**Confidence: high** on the primitives and Anthropic's guidance; **medium-high** on tier direction; **low** on any per-task Haiku 5.5 measurement (none independent).

**Primitives and Anthropic's harness shape.** "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read." (https://code.claude.com/docs/en/sub-agents); "Model to use: `sonnet`, `opus`, `haiku`, `fable`, a full model ID such as `claude-opus-5-5`, or `inherit`." (same page); "To restrict tools, use the `tools` field as an allowlist or the `disallowedTools` field as a denylist." (same page); "each subagent spends tokens of its own while it runs." (same page); "`CLAUDE_CODE_SUBAGENT_MODEL` (+ `_FORCE`) runs every subagent on one model" (/home/user/Autonomy-Research/research/findings/architecture.md:53). Cost guidance: "Reserve Opus for complex architectural decisions or multi-step reasoning." and "For simple subagent tasks, specify `model: haiku`" (https://code.claude.com/docs/en/costs); "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode" (same page); "Delegate these to subagents so the verbose output stays in the subagent's context while only a summary returns to your main conversation." (same page). Anthropic's long-running harness uses "an initializer agent that sets up the environment on the first run, and a coding agent that is tasked with making incremental progress in every session" and admits "it's still unclear whether a single, general-purpose coding agent performs best across contexts, or if better performance can be achieved through a multi-agent architecture." (https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); the later planner/generator/evaluator harness says the evaluator "is worth the cost when the task sits beyond what the current model does reliably solo.", "The harness was over 20x more expensive, but the difference in output quality was immediately apparent.", and "the evaluator is still an LLM that is inclined to be generous towards LLM-generated outputs." (https://www.anthropic.com/engineering/harness-design-long-running-apps). `/goal`'s evaluator "runs on whichever provider your session is configured for. It does not call tools, so it can only judge what Claude has already surfaced in the conversation." (https://code.claude.com/docs/en/goal). The research-agent result stands: "Anthropic's Research system (Opus lead + Sonnet workers) beat single-agent Opus by 90.2% on an internal breadth-first eval, but at roughly 15x chat token cost" (/home/user/Autonomy-Research/research/findings/architecture.md:3). Worker inference: for coding the right shape is sequential roles with file hand-off (plan file, progress file, git), not parallel peers; parallel fan-out only for read-only work (search, test runs, review); the evaluator should be switchable per task class and re-measured at each model release.

**What cheap models do well and badly.** Haiku 5.5 "pairs well with Opus 5.5 and Sonnet 5.5 as a subagent on coding work." but "Sonnet 5.5 and Opus 5.5 remain better choices for complex agentic coding tasks like those measured by Terminal-Bench 4.0." (https://www.anthropic.com/claude-haiku-5-5); the WebFetch paraphrase of that page's table reads "Haiku 5.5 scored 39.2%, and Sonnet 5.5 scored 70.6%." (same page; paraphrase, medium confidence). The product page says "Haiku 5.5 is a fast, cost-efficient subagent for coding and well-defined tasks." and, as WebFetch summary text, "The only SWE-bench figure is for Haiku 4.5: 73.3% on SWE-bench Verified." (https://www.anthropic.com/claude/haiku). Worker inference (not in the quoted lines): the same fetch reported Haiku 5.5 at $0.10 / $0.50 per million input/output tokens up to 100K prompt tokens. A cheap scout handing off to a strong fixer matched the best single model: "SuperScout matches the best single model's solve rate (159 of 266 for SuperScout, 158 for the best model)." and "A no-router ablation, always the cheapest fixer with the handoff, ties the routed system on this benchmark." (https://arxiv.org/html/2608.04804v1); worker inference (not in the quoted lines): the same fetch reported cost per solve of $0.230 vs $1.274 for Opus 4.6 alone.

**Reviewers and verifiers.** "Official execution evidence shows the potential of weak review when decisive checks are available." and "Reviewer size is not a consistent predictor of quality." (https://arxiv.org/html/2610.01023); "A lightweight cross-model reviewer scores no higher than same-model review." yet "one CCR plus one XMR review covers more ground-truth errors than two CCR reviews (56.7% vs. 42.7%)." (https://arxiv.org/html/2610.01471v1); Anthropic observed "Claude's tendency to mark a feature as complete without proper testing." (https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); "Adding a high-level task-objective verification step to ChatDev gave +15.6% task success [MAST]." (/home/user/Autonomy-Research/research/findings/architecture.md:15). Worker inference: a cheap verifier should check what can be tested mechanically (exit codes, file exists, quote present), not judge quality; a Haiku code reviewer has no support in the evidence; for correctness, put the money into tests and an e2e run, then a Sonnet/Opus-class reviewer with fresh context and no write tools.

**What the repo already settles.** Researcher "model: sonnet" / "maxTurns: 40" / "omitClaudeMd: true" (/home/user/Autonomy-Research/plugin/agents/researcher.md:4-7); verifier "model: haiku" and "never more than 20 claims" (plugin/agents/verifier.md:4-6) with "An uncertain judgment counts as unverified." (verifier.md:34); synthesizer "model: inherit" (plugin/agents/synthesizer.md:4-6); spike worker "You are the one agent allowed to install or run a candidate." (plugin/agents/spike-worker.md:18); prior rulings "*Haiku workers by default*: not adopted; Anthropic's data says worker model quality beats token budget, and Haiku is reserved for the verifier and for trivially bounded tasks." (architecture.md:128) and "*Agent teams with peer messaging*: rejected for now; docs say roughly 7x tokens, experimental and disabled by default" (architecture.md:125); the inherited open question "the degradation slope for the models this plugin will actually run is unmeasured." (architecture.md:148).

### Q4. How should loops be bounded, how is a stuck run detected, and how does the end state reach an absent operator?

**Confidence: high** on documented caps and defaults; **medium-high** on stall detection (one implementation opened); **medium** on end-state reporting (one real overnight audit).

**Every bound defaults to none.** `--max-turns`: "Limit the number of agentic turns (print mode only). Exits with an error when the limit is reached. No limit by default." (https://code.claude.com/docs/en/cli-reference); `--max-budget-usd`: "Spend can pass the cap, so leave headroom." (same page); the SDK: "When either limit is hit, the SDK returns a `ResultMessage` with a corresponding error subtype (`error_max_turns` or `error_max_budget_usd`).", "Setting a budget is a good default for production agents.", and "Spend can therefore pass the cap by up to the cost of that one response, plus anything that subagents still running at that moment spend" (https://code.claude.com/docs/en/agent-sdk/agent-loop). The Ralph plugin's zero means infinite with no no-op check (Q1, https://github.com/anthropics/claude-plugins-official/issues/1699), and the issue proposes that "`/ralph-loop` without `--max-iterations` defaults to a non-infinite cap (suggested 1000), with explicit opt-in for unbounded". `/goal` is a prompt-based Stop hook: "If Claude keeps answering the evaluator without making progress (no tool use for several turns in a row), Claude Code stops the loop, prints a warning", "To bound how long a goal runs, include a turn or time clause in the condition, such as `or stop after 20 turns`.", and "It doesn't run commands or read files independently, so write the condition as something Claude's own output can demonstrate." (https://code.claude.com/docs/en/goal). Anthropic's loop guidance: "Setting a specific completion criteria and explicit turn caps, “stop after 5 tries.”" (https://claude.com/blog/getting-started-with-loops). Headless runs stop background work "after 10 minutes of continuous idle waiting by default and drops its partial result." (https://code.claude.com/docs/en/headless). Stop hooks must guard themselves: "if [ "$(echo "$INPUT" | jq -r '.stop_hook_active')" = "true" ]; then" (https://code.claude.com/docs/en/hooks-guide), and the eight-block override "then ends the turn with a warning that the Stop hook blocked too many consecutive times." (same page). A practitioner's designed-up-front rule was "two attempts per ticket, then stop" (https://yoheinakamura.dev/night-loop-audit/). Worker inference (loop note): the plugin's `max_iterations` counts Stop-hook continuations inside one session and cannot cap spend when the session itself restarts (the Docker-restart case), so the outer supervisor must own a total-attempt counter in a file outside the container; the three layers need different units: per attempt (`--max-turns`, `--max-budget-usd`, `timeout`), per task (2 attempts), per night (total USD and wall clock).

**Stuck-run detection.** frankbria/ralph-claude-code implements a circuit breaker: "CB_NO_PROGRESS_THRESHOLD=${CB_NO_PROGRESS_THRESHOLD:-3}", "CB_SAME_ERROR_THRESHOLD=${CB_SAME_ERROR_THRESHOLD:-5}", "CB_COOLDOWN_MINUTES=${CB_COOLDOWN_MINUTES:-30}", with progress meaning "# Git shows uncommitted changes - clear progress" and the error test being only "if [[ "$has_errors" == "true" ]]; then" (https://raw.githubusercontent.com/frankbria/ralph-claude-code/main/lib/circuit_breaker.sh). Issue 1699 proposes hashing identical outputs, which "would have caught my incident at iteration 3 instead of iteration 6,239." (https://github.com/anthropics/claude-plugins-official/issues/1699). `/usage` shows "a row for each of the heaviest `/loop` or other scheduled tasks that ran recently, ordered by total tokens" (https://code.claude.com/docs/en/costs). The 71% post's forensic signal was git artifacts, and "Stateless restarts compound the problem." (https://www.adrosenfeld.com/blog/2026-02-16-when-your-agent-burns-71-percent-of-your-tokens/). Worker inference: cheap deterministic signals for a supervisor are `git diff --stat` or new-commit count per attempt, `git rev-parse HEAD` unchanged, SHA-256 of final result text equal across attempts, hash of the failing-test set equal across attempts, and `num_turns` and `total_cost_usd` from the result JSON; a change in the failing-test set is better "same error" evidence than a boolean; test-count progress is implemented nowhere opened and is a spike item.

**End state for an absent operator.** "The `subtype` field (available in both SDKs) is the primary way to check termination state." and "All result subtypes carry `total_cost_usd`, `usage`, `num_turns`, and `session_id` so you can track cost and resume even after errors." with the example "Agent ran out of turns. Resume with a higher limit." (https://code.claude.com/docs/en/agent-sdk/agent-loop); "Claude Code exits with code 0 on success and a non-zero code when the run fails, so your scripts can branch on the exit status." and on SIGTERM "Claude Code exits with code 143. Claude Code leaves the turn that was in progress unfinished and records no result for it." (https://code.claude.com/docs/en/headless); a crash "may carry zeroed `usage`, `total_cost_usd`, and `modelUsage`, so recover the call's totals from what arrived before it." (https://code.claude.com/docs/en/agent-sdk/cost-tracking); for a long `/goal` "a goal that runs many turns can look stuck. Add `--output-format stream-json --verbose` to emit each message as the loop runs.", status shows "How many turns have been evaluated", and errors read "Goal cleared after an unrecoverable error" (https://code.claude.com/docs/en/goal); the Notification hook "fires when Claude is waiting for input or permission." (https://code.claude.com/docs/en/hooks-guide). The overnight audit used "1 note = 1 decision request", a digest that "preserves a per-run summary", and admits "per-run token cost was not measured." (https://yoheinakamura.dev/night-loop-audit/). Worker inference: define four terminal states and write one `RUN_STATUS.json` from a `trap` handler before exit, because SIGTERM and crashes record no result: `done` (acceptance script passed), `blocked` (reason plus one decision request), `stopped_by_bound` (which bound), `crashed`; include `session_id`, git HEAD, a per-task table, `total_cost_usd` (estimate) and the last breaker reason; push one message at terminal state only; "done" must be script-checked, since `/goal`'s evaluator sees only what Claude surfaces.

**Contradictions.** ghuntley frames Ralph as an unbounded `while` loop (https://ghuntley.com/ralph/); the Anthropic plugin README and loop blog require explicit caps (https://github.com/anthropics/claude-code plugins/ralph-wiggum/README.md:134 (commit 03b5892), https://claude.com/blog/getting-started-with-loops). Not a factual conflict: the bound is the operator's job; settled by making the cap mandatory in the supervisor.

### Q5. Which token practices hold outcome quality?

**Confidence: high** on documented prices and practices; **medium** on effect sizes (no controlled measurement of any trimming practice in an opened source).

**Caching.** "Cache read tokens are 0.1 times the base input tokens price (see the table footnote for per-model exceptions)", "5-minute cache write tokens are 1.25 times the base input tokens price", "1-hour cache write tokens are 2 times the base input tokens price", "The cache is refreshed for no additional cost each time the cached content is used.", and "Shorter prompts cannot be cached, even if marked with `cache_control`." (https://platform.claude.com/docs/en/build-with-claude/prompt-caching); the footnote as relayed by WebFetch: "Cache hits and refreshes ... are priced at 0.05x the base input price." for Opus 5.5 and Sonnet 5.5. In Claude Code, "Unless you choose a TTL yourself, Claude Code requests the one-hour TTL only on a Claude subscription within your plan's included usage.", "If you sign in with an API key or use a cloud provider, set `promptCacheTtl` to `1h` to give the main conversation a one-hour cache.", "Each model has its own cache. Switching with `/model` means the next request reads the entire conversation history with no cache hits", "In Claude Code, the cache is effectively scoped to one machine and directory.", "Sequential sessions share the prefix only when the git status snapshot taken at startup matches", "Sessions you run in parallel in the same directory build matching prefixes and read each other's cache.", and "After a break longer than the cache lifetime, there is no cache left to read, so the summarization request reprocesses the full history as uncached input." (https://code.claude.com/docs/en/prompt-caching). `--exclude-dynamic-system-prompt-sections` "Improves prompt-cache reuse across different users and machines running the same task." (https://code.claude.com/docs/en/cli-reference).

**Costs and windows.** "the average cost is around $13 per developer per active day and $150-250 per developer per month, with costs remaining below $30 per active day for 90% of users." (https://code.claude.com/docs/en/costs); "Thinking tokens are billed as output tokens, and the default budget can be tens of thousands of tokens per request depending on the model." (same page); "Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions or multi-step reasoning." (same page); background processes cost "typically under $0.04 per session" (same page). Cost fields are estimates: "Both figures are client-side estimates and can differ from your actual bill." (https://code.claude.com/docs/en/headless) and "Do not bill end users or trigger financial decisions from these fields." (https://code.claude.com/docs/en/agent-sdk/cost-tracking). Native-1M models "compact before the window fills, at about 967K tokens by default." and "The command and the flag accept a window size from 100K to 1M tokens" (https://code.claude.com/docs/en/model-config). Bash output is "Inline up to roughly 30,000 characters by default; past that, the path of a file saved to the session directory", failing commands "Inline up to roughly 10,000 characters; past that, a head-and-tail excerpt of that size", the ceiling "up to 128,000 characters", and the default timeout is "the default when Claude passes no timeout; two minutes out of the box" (https://code.claude.com/docs/en/tools-reference). On a subscription, a usage limit pauses the run: "After three automatic retries, the goal pauses instead." (https://code.claude.com/docs/en/goal).

**Practices.** Hook-filtered test output, "reducing context from tens of thousands of tokens to hundreds." (https://code.claude.com/docs/en/costs); "Use `/clear` to start fresh when switching to unrelated work. Stale context wastes tokens on every subsequent message."; "Aim to keep CLAUDE.md under 200 lines by including only essentials."; "Vague requests like \"improve this codebase\" trigger broad scanning."; "When Claude can verify its own work, it catches issues before you need to request fixes."; "Claude Code sends your full conversation with every request"; "Tools like `gh`, `aws`, `gcloud`, and `sentry-cli` are still more context-efficient than MCP servers" (all same page). "Persistent rules belong in CLAUDE.md (loaded via `settingSources`) rather than in the initial prompt, because CLAUDE.md content is re-injected on every request." (https://code.claude.com/docs/en/agent-sdk/agent-loop). "`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." (https://code.claude.com/docs/en/headless). "Expensive preambles multiply costs." (https://www.adrosenfeld.com/blog/2026-02-16-when-your-agent-burns-71-percent-of-your-tokens/). Worker inferences (loop note): narrow tasks in a fresh `-p` session each, with state on disk, give a small context and a restartable unit, and sequential runs in one directory can share the prefix if git status matches; on a Max subscription the 1-hour TTL applies until plan usage is exhausted, so set `promptCacheTtl=1h` when long test suites leave gaps over 5 minutes; `--max-budget-usd` is advisory on subscription plans, so wall-clock and turn caps matter more; quality-safe trims are filtering passing-test noise and truncating logs while keeping failing output whole; unsafe trims are dropping the stack-trace head or lowering effort on planning and debugging; every trim should be A/B tested before becoming default.

**Contradictions.** The costs page says caching reduces cost automatically, while the cache lifetime is 5 minutes for API-key runs unless `promptCacheTtl` is set (https://code.claude.com/docs/en/costs, https://code.claude.com/docs/en/prompt-caching). A scope mismatch, not a conflict: plan for 5 minutes, do not assume 1 hour.

**Spike list (what must be tried for real before building).**
1. Context-rot onset on the target model: a fixed multi-requirement task set with a 20-30 item acceptance checklist at clean vs 150K vs 400K context, 10 runs each, measuring strict pass and requirement coverage.
2. Compaction fidelity: seed decisions, force `/compact` and auto-compact, diff decisions in the summary, with and without Compact Instructions and a SessionStart `compact` hook re-injecting the ledger; also whether the Superpowers ledger survives a real compaction on a long plan.

8. Completion honesty and trimming: rate of "done" claims with failed checks with and without a Stop-hook verifier; effect of a tool-output truncation hook on pass rate and tokens; cache hit rate across sequential `-p` runs in one directory.
