# Engineer intake: from a messy spoken brief to an approved, feasible design

Run: research/runs/engineer-intake/PLAN.md. Notes: research/runs/engineer-intake/notes/ (four workers; all web sources opened 2026-10-16, mostly with Parallel web_fetch, some with WebFetch or curl; repo lines read locally).

The evidence favours a two-phase, budgeted intake run as prompt and file structure inside Claude Code, with nothing to install. Phase 1 is open and specific-past: the model takes John's dictated rant, then asks one "tell me about the last time" question per turn (https://www.nngroup.com/articles/interview-questions-mistakes/, https://www.nngroup.com/articles/open-ended-questions/), probing backward along a JTBD-style timeline (https://jobstobedone.org/the-timeline/) over a fixed coverage list, because free-form LLM interviewing finds "less than half of the users' implicit requirements" and finds them late (https://arxiv.org/abs/2602.18306v1) while a fixed slot structure measured better (https://arxiv.org/html/2605.05828). Phase 2 is closed gap-closing in the spec-kit `/clarify` shape: one question at a time, 2-5 options with a marked recommendation and a plain "why it matters" line, a hard cap of 5, a Deferred list for what is left (https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md). Before planning, the engineer restates "do X with tool Y" as a question about the underlying problem (framing a statement as a question beat a "don't be sycophantic" prompt, https://arxiv.org/pdf/2602.23971; strong models "predominantly answer the literal request", https://arxiv.org/abs/2609.06842), captures goal, constraints and ruled-out options (https://xyproblem.info/), shows a comparison table of at most 5 options (https://www.nngroup.com/articles/comparison-tables/) with explanation-style term cards (https://diataxis.fr/explanation/), pushes back once with the concrete cost and then respects John's call while recording the objection in an ADR-style entry (https://www.anthropic.com/constitution, https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions). On "I don't know", the intake dispatches the existing research skill for a verified option map instead of recording a gap, since LLMs "overwhelmingly default to direct answers" rather than ask (https://www.alphaxiv.org/abs/2605.25284) and deep-research citation URLs are hallucinated at 3-13% (https://arxiv.org/abs/2604.03173v1). The artifact is a short human spec (goal, EARS requirements each with a fit criterion, acceptance scenarios, constraints, deferred list, glossary, decision log; https://alistairmavin.com/EARS, https://www.reqview.com/blog/2019-02-27-news-volere-requirements-specification-template, https://kiro.dev/docs/specs/feature-specs/requirements-first/) plus a machine-owned JSON task list with a `passes` field (https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents). The current interview skill is a pure open-question conversation with no budget, no option menus and reconnaissance only on request (/home/user/Autonomy-Research/plugin/skills/interview/SKILL.md:9-10, :17-18, :47-48), so it must gain the explore branch, the closed gap-closing phase, a budget and a plan-approval checkpoint. Confidence overall: medium; no opened study tests any of this with a non-expert dictating by voice, and the numeric budgets are worker proposals that need a spike.

## Questions and answers

### Which elicitation method, question style and stopping rule?

Confidence: medium.

**Method.** Two methods have opened evidence of producing testable output and of use in LLM spec flows. EARS is a small set of plain-English clause patterns ("When <trigger>, the <system name> shall <system response>", https://alistairmavin.com/EARS) with a strict ruleset (zero or many preconditions, zero or one trigger, one system name, one or many responses, same URL); Kiro generates user stories plus EARS behaviours and claims (vendor claim) they are "Unambiguous and testable" and "Clear for both technical and non-technical stakeholders" (https://kiro.dev/docs/specs/feature-specs/requirements-first/). Volere makes a requirement testable by a fit criterion: "If a fit criterion cannot be found for a requirement, then the requirement is either ambiguous or poorly understood" (https://www.reqview.com/blog/2019-02-27-news-volere-requirements-specification-template, a 2019 secondary blog). JTBD's switch timeline and story-map backbone are interview structures rather than output formats: the JTBD interviewer keeps "probing backward, asking “what was going on before that?”, until you reach the true beginning" and the timeline "gives you a structure to organize the story even as it comes out in pieces, so you always know where the gaps are" (https://jobstobedone.org/the-timeline/); story mapping goes "mile- wide, inch deep" first (https://www.jpattonassociates.com/wp-content/uploads/2015/03/story_mapping.pdf). LLM interviewers exist: LLMREI (GPT-4o prompts, 33 simulated interviews with students) "makes a similar number of errors compared to human interviewers" and found that "the non-fine-tuned models clearly outperformed the fine-tuned ones" (https://arxiv.org/html/2507.02564v1). But free-form LLM interviewing is weak: across 101 website scenarios and 7 LLMs, interviewers "elicit less than half of the users' implicit requirements, and their effective elicitation questions often emerge in later turns of the dialogue" and "consistently struggle with style-related requirements" (https://arxiv.org/abs/2602.18306v1). A structured slot ontology did better: "OntoAgent achieves an IRE of 0.69, outperforming all baselines. The strongest baseline ( i.e., Mistake-guided Prompting) reaches 0.52" (https://arxiv.org/html/2605.05828; web-app domain only). Worker inference (elicitation note): a non-expert cannot write EARS, but the model can draft EARS or Given/When/Then lines from John's story and read them back in plain words; the intake should carry a fixed slot list rather than rely on improvisation.

**Question style.** NN/g (2024): "The greatest benefit of open-ended questions is that they allow you to find more than you anticipate"; "Use closed questions to gather additional small details, gain clarification, or when you want to analyze responses quantitatively"; "Leading closed questions often start with the words “did,” “was,” or “is.” Open-ended questions often begin with “how” or “what.”"; and the funnel, where sessions "begin with broad, open-ended questions before introducing specific, closed questions" (https://www.nngroup.com/articles/open-ended-questions/). NN/g (2022): "It’s much better to ask about specific examples than to ask them to describe what they think is typical"; hypotheticals are unreliable because "people are bad at predicting their future behavior or choices — but they’ll likely have a good answer for you!"; "avoid asking questions that use the word ‘because.’"; and one question at a time: "keep questions short and concise, and don’t ask people to tell you what they did and why; that’s what followup and probing questions are for!" (https://www.nngroup.com/articles/interview-questions-mistakes/). LLMREI saw the matching failure: "the bot often asked multiple questions simultaneously, overwhelming stakeholders" (https://arxiv.org/html/2507.02564v1). For the gap-closing phase, spec-kit `/clarify` requires that "Each question must be answerable with EITHER: A short multiple‑choice selection (2–5 distinct, mutually exclusive options), OR A one-word / short‑phrase answer", adds "one plain-language \"Why it matters\" sentence (the stake for acceptance or shipping) before the recommendation/options", presents "EXACTLY ONE question at a time", formats "`**Recommended:** Option [X] - <reasoning>`" and lets the user "accept the recommendation by saying \"yes\" or \"recommended\"" (https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md). Claude Code's own best-practices page has the interview prompt say "Don't ask obvious questions, dig into the hard parts I might not have considered" (https://code.claude.com/docs/en/best-practices).

**Stopping rule.** Three rules appear in opened sources. Coverage plus a cap: OntoAgent stops "until no eligible slots remain in $\mathcal{T}$ or a predefined maximum number of turns is reached", reports "often eliciting key implicit requirements within the first 3–5 turns, while free-form baselines typically exhibit prolonged stagnation in the initial dialogue phase", and finds that pruning low-yield branches "does not harm coverage. Instead, it improves IRE" (https://arxiv.org/html/2605.05828). Hard cap with user stop: spec-kit stops "when: All critical ambiguities resolved early (remaining queued items become unnecessary), OR User signals completion (\"done\", \"good\", \"no more\"), OR You reach 5 asked questions", ranks by "(Impact * Uncertainty)", marks each category "Clear / Partial / Missing", and "If quota reached with unresolved high-impact categories remaining, explicitly flag them under Deferred with rationale" (https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md). Saturation is weak as a rule: "The strict notion of complete saturation as the point where few or no new ideas are observed is not a useful concept to guide sample size decisions", though "Even small samples (n = 10) produced 95% of the most salient ideas with exhaustive listing" (https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0198606, 2018, about number of respondents, not turns; the transfer to per-question stopping is the worker's extrapolation). Worker inference (elicitation note): stop when every heading of the coverage list is Clear or explicitly Deferred, or John says done, or a cap is hit; the worker proposes roughly 5 gap-closing questions after the rant (the 5 is spec-kit's) and an overall turn cap. Worker inference (not in the source): the note states OntoAgent's experiments cap at 20 turns, but the quoted line does not give that number. The worker's added diminishing-yield check (two consecutive answers add no new requirement or entity) is unsourced.

**Voice input.** John dictates; coined tool names are the hazard. Google's conversation design guidance: use explicit confirmation "sparingly, only when the cost of misunderstanding the user is high, for example, names, addresses, texts to be shared on the user’s behalf" (https://developers.google.com/assistant/conversation-design/confirmations). The tau-Elicitation benchmark (2026-09-15, simulated callers) finds "misunderstood named entities impede spoken dialogue, while confirming every attribute can itself frustrate callers"; "A scaffold that prescribes spelling, read-back, correction, and confirmation raises robust $\mathrm{Pass}^{3}$ by 14–31 points, at a cost of 21–28 seconds per call"; "Pooled $\mathrm{Pass}^{3}$ ranges from 1.7% for medications and 3.3% for coined names to 46.7% for phone numbers and 60.0% for dates"; "Agents often double down on an error or hallucinate a replacement rather than complete the repair"; and "A matched text run passes all 200 tasks, implicating spoken capture and repair rather than task understanding" (https://arxiv.org/html/2609.13602v1). Worker inference (elicitation note): the transfer is partial because John's input is his own STT text, not a live voice agent; keep a glossary seeded from John's known tools and the repo, fuzzy-match unknown nouns silently, auto-accept high-confidence matches, batch low-confidence or coined names into one end-of-rant playback list, never ask about generic words, and require explicit confirmation only for names with irreversible cost.

**Contradictions.** NN/g says closed questions should be sparing and can lead (https://www.nngroup.com/articles/open-ended-questions/), while spec-kit `/clarify` is almost entirely closed (multiple choice, short answers; https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md). The elicitation worker reads this as two phases (discovery vs gap-closing), not a true conflict, and the evidence favours that reading since NN/g itself describes the funnel from open to closed; a spike should still test whether a recommended-option choice biases John toward the model's default. Google says confirm rarely (https://developers.google.com/assistant/conversation-design/confirmations) while tau-Elicitation shows confirmation lifts accuracy at a time and annoyance cost (https://arxiv.org/html/2609.13602v1); the worker resolves this by risk-tiering, which both sources support (Google names names and addresses as the high-cost cases).

### What do current agentic coding tools do at intake, and what fails?

Confidence: medium-high for structure and for verbosity and size-mismatch failures (multiple independent sources); medium for anchoring on the user's wording (no direct source).

**Three families** (agentic-tool worker's grouping). ### How does the engineer push back on asks that do not fit the goal and avoid sycophancy?

Confidence: medium-high on the mechanisms (papers are on chat benchmarks, not agentic coding); medium on process detail.

Sycophancy is general and trained in: "our results indicate that sycophancy is a general behavior of state-of-the-art AI assistants, likely driven in part by human preference judgments favoring sycophantic responses" (https://arxiv.org/abs/2310.13548). OpenAI rolled back an update after "User feedback in particular can sometimes favor more agreeable responses, likely amplifying the shift we saw" (https://openai.com/index/expanding-on-sycophancy/). Anthropic: "We think the results reflect a trade-off between model warmth or friendliness on the one hand, and sycophancy on the other" and "sycophantic AI models tend to abandon correct positions under pressure" (https://www.anthropic.com/news/protecting-well-being-of-users). What measurably helps: input framing. Converting the user's statement into a question reduced sycophancy, and "Importantly, this effect is stronger than a simple baseline prompt asking models “not to be sycophantic”"; sycophancy "increases monotonically with epistemic certainty conveyed by the user, and (3) is amplified by I-perspective framing" (https://arxiv.org/pdf/2602.23971). Reasoning helps with a caveat: "reasoning generally reduces sycophancy in final decisions but also masks sycophancy in some samples", and "a non-trivial proportion of sycophantic switches still involve abandoning a correct answer, representing a direct loss of truthfulness or accuracy" (https://aclanthology.org/2026.acl-long.1126.pdf). The XY problem is measurable in LLMs: "even the strongest LLMs predominantly answer the literal request (0.75--0.92)" and "Oracle ablation experiments show that providing explicit user intent at generation time helps" (https://arxiv.org/abs/2609.06842). Agents gain from asking but "models struggle to distinguish between well-specified and underspecified instructions", with interaction yielding "up to 74%" gains (https://arxiv.org/abs/2502.13069). The canonical XY remedy: "The XY problem is asking about your attempted solution rather than your actual problem."; the asker should "share why you've ruled them out. This gives more information about your requirements"; the answerer's symptom is that "Y seems like a strange problem to want to solve" (https://xyproblem.info/). Anthropic's constitution tells Claude to be "diplomatically honest rather than dishonestly diplomatic", to infer "The deeper motivations or objectives behind their immediate request", and that "Claude can voice its concerns but should nonetheless respect the wishes of the user" (https://www.anthropic.com/constitution). Constraints behind odd asks fit the ADR shape: the context "describes the forces at play, including technological, political, social, and project local"; "A decision may be "proposed" if the project stakeholders haven't agreed with it yet, or "accepted" once it is agreed."; "The motivation behind previous decisions is visible for everyone, present and future."; and "All consequences should be listed here, not just the "positive" ones." (https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions).

Worker inferences (pushback note): when John dictates "do X with tool Y", the agent restates it internally as a question ("what problem is X meant to solve, and what are the ways to solve it?") and a separate step writes the underlying goal; do not rely on a "don't be sycophantic" line alone; because reasoning can rationalise, check the output with an artefact (an options table with at least one non-user option, a goal statement John confirms); push back only where the ask conflicts with the stated goal or a constraint, since excessive pushback annoys users. For "dockerize this website", the first move is to ask what outcome is wanted (host it, share it, make it repeatable, satisfy an organisational rule) and what has been tried or ruled out, then show options; the agent needs a quick test of whether the literal ask serves the stated goal, and if so, do it. Insist protocol: one-paragraph objection with the concrete cost to John's goal; the alternative and the cheapest test; if John still insists, proceed; write an "accepted over objection" ADR with objection, risk and a trigger to revisit; do not reopen unless the risk materialises; never retract the objection from the record under pressure. Constraint entry fields: statement in John's words, source (John said / inferred), type, hard or soft, what it rules out, date, status (proposed until John confirms); inferred constraints are proposed and confirmed once, since a wrong inferred constraint silently removes good options.

**Contradictions.** None between opened sources. Two caveats, not conflicts: reasoning both reduces and masks sycophancy (https://aclanthology.org/2026.acl-long.1126.pdf), and Anthropic reports more pushback can feel excessive (https://www.anthropic.com/news/protecting-well-being-of-users).

### How does it teach the options the user did not know and help narrow the search space?

Confidence: medium on formats and structure; high on the verification risk; low on effect sizes (none opened).

Non-technical choice format: "When more than 5 items need to be compared, add other mechanisms such as filters to help users narrow down the larger set of possibilities to 5 or fewer."; "The biggest problem with most comparison tables isn’t design, it’s content"; "When using text within comparison tables, keep it short. Whenever possible, avoid full sentences." and "include links to more information or in-context tooltips with definitions or clarifying information" (https://www.nngroup.com/articles/comparison-tables/). Progressive disclosure "helps prioritize their attention so that they spend time only on features that are most likely to be useful to them" (https://www.nngroup.com/articles/progressive-disclosure/). Teaching cards should be Diátaxis explanation: "Explanation can and must consider alternatives, counter-examples or multiple different approaches to the same question." (https://diataxis.fr/explanation/). Guided-exploration patterns with support: Gemini Deep Research's collaborative planning, "letting you review and refine the research plan before execution. When enabled, the agent returns a proposed research plan instead of executing immediately." (https://ai.google.dev/gemini-api/docs/deep-research); Sensecape (UIST 2023, small within-subject study) "empowers users to explore more topics and structure their knowledge hierarchically, thanks to the externalization of levels of abstraction" (https://dl.acm.org/doi/10.1145/3586183.3606756); TrailLM (Aug 2026 prototype, no controlled results: "The next step will be to run a controlled user study.") argues "users often struggle to translate their goals into the detailed prompts needed to use these systems effectively", that "users must reflect on their metacognitive processes to recognize what they know, identify knowledge gaps, and deliberately regulate their search", and that "users receive a direct answer to an initial, often underdeveloped prompt, which may encourage them to bypass the critical process of iterative sensemaking" (https://arxiv.org/html/2607.11810v1). The agent must be told to ask: "models often identify ambiguity when explicitly asked to judge it, yet in the QA setting they overwhelmingly default to direct answers", and "Retrieved context further widens this gap by improving answerability while making models even less likely to ask clarifying questions" (https://www.alphaxiv.org/abs/2605.25284). Candidates from research need checking: "We find that 3--13\% of citation URLs are hallucinated -- they have no record in the Wayback Machine and likely never existed -- while 5--18\% are non-resolving overall." and "models equipped with urlhealth reduce non-resolving citation URLs by $6\textrm{--}79\times$ to under 1\%" (https://arxiv.org/abs/2604.03173v1). The official MCP registry search is "Case-insensitive substring search on server names (e.g., `filesystem`)" and "This is intentionally simple. For more advanced searching and filtering, use a subregistry." (https://raw.githubusercontent.com/modelcontextprotocol/registry/main/docs/reference/api/official-registry-api.md:41-42); spam is handled by reports ("What if I need to report a spam or malicious server?", https://raw.githubusercontent.com/modelcontextprotocol/registry/main/docs/modelcontextprotocol-io/faq.mdx:52-54); a live query for "browser" returned unvetted listings including "pay-per-call x402 tools, no API keys" (registry.modelcontextprotocol.io/v0.1/servers?search=browser, curl).

Worker inferences (pushback and unknown-unknowns notes): an option map with one row per option (max 4 plus "do nothing/what you asked"), columns for what it is in one line, effort for John, cost, what it needs from his organisation, risk and "good if", the recommended row marked, each unfamiliar term a one-line explanation card below the table; teaching cards are explanation, not tutorial, because John needs to choose, not operate; offer a diagram only after he picks (judgement, no source). A "map first, then ask" loop (agent shows a short option map, John reacts, agent narrows) fits the evidence better than open questions alone because reacting to options is easier than generating requirements; questions that most reduce the remaining option set come first (e.g. "must it run unattended?" before "which framework?"); every candidate passes a verify step (URL resolves, repo exists, last commit date, star count) before it reaches John; for a novice the larger risk is a real but stale or irrelevant tool recommended with confidence. Worker inference (not in the source): one landscape pass of at most the existing 5-worker landscape row in the background while the interview continues, one page of at most about 5 options per dimension, at most about 3 option-narrowing rounds, then leftovers recorded as gaps; these numbers are untested.

**Contradictions.** None among opened sources. The two package-hallucination rates the unknown-unknowns worker compared both rest on search excerpts only and are excluded (see Open questions).

### What does the intake artifact contain?

Confidence: medium-low (formats are evidenced; no source shows which artifact parts improve a coding model's output).

Kiro's requirements.md holds "User stories with clear acceptance criteria; System behaviors in EARS format (WHEN...THE SYSTEM SHALL...); Functional requirements; Edge cases and error handling", with error-path lines such as "WHEN a user submits an email that already exists THE SYSTEM SHALL display \"Email already registered\" error", and its vague-spec advice is "Include specific user scenarios and edge cases; Define clear success criteria" (https://kiro.dev/docs/specs/feature-specs/requirements-first/); EARS lines are "Easy to translate into test cases" (https://kiro.dev/docs/specs/feature-specs/requirements-first.md). spec-kit writes answers back into the spec ("Keep each inserted clarification minimal and testable (avoid narrative drift)."), ends with a "Coverage summary table listing each taxonomy category with Status: Resolved (was Partial/Missing and addressed), Deferred", and its taxonomy includes "Edge Cases & Failure Handling: Constraints & Tradeoffs: Terminology & Consistency: Completion Signals:" (https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md). ## Implications for the researcher plugin

- The interview skill becomes an intake protocol with two question phases: keep the open, one-question-per-turn rule for discovery (U15, E14-E21) but add a closed gap-closing phase in the spec-kit `/clarify` shape, one question per AskUserQuestion call, recommended option first, a "why it matters" line, a cap of 5 and a Deferred list (E23, E24, A24-A27, E28, E29). Because AskUserQuestion is unavailable in subagents (A30), intake runs in the main session.
- Add an explore branch: on "I don't know" or when John names a tool, the skill queues a facet for the existing research skill (U22) rather than recording a gap (U20) or waiting to be asked (U19), and shows a verified table of at most 5 options with explanation-style term cards (P15-P19). Every candidate passes a URL/repo check before John sees it (U7, U8, U11).
- Add a restate-as-question step and a goal/constraints/ruled-out-options record before any survey (P5, P9, P12, P13); push back once with the concrete cost, then respect the call and write an "accepted over objection" ADR entry (P24, P20-P22, P25). Do not rely on a "don't be sycophantic" line alone (P5).
- Replace the unbounded conversation with a stopping rule: coverage list Clear or Deferred, user says done, or cap reached (E25, E28-E30). The specific caps are worker proposals and need a spike. The five-whys probe (U16) should follow the option map, not precede it (worker inference).
- Output two artifacts: a Markdown spec (goal, EARS requirements each with a fit criterion, acceptance scenarios, constraints, deferred list, glossary, decision log; E1-E5, E34-E39) and a JSON task list with a `passes` field and a verification command per item (A34-A38). Record approval in a file plus a script-checked state, not via ExitPlanMode alone (A20-A22).
- Add a single batched glossary playback for dictated names, seeded from the repo and John's known tools, with explicit confirmation only for names with irreversible cost (E42-E47; worker inference).
- Size-gate: a one-sentence diff skips intake entirely (A1, A43, A44). Keep the skill file short; long instruction files get ignored (A18).
