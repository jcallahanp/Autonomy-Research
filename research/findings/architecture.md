# Research-agent architecture: parallel subagents vs single agent, merging, and context rot

The evidence favours a **small orchestrator-worker fan-out whose workers write cited notes to files, followed by a single-threaded synthesis step**, and it argues against both a single long-context agent for multi-topic research and against "many agents talking to each other". Anthropic's Research system (Opus lead + Sonnet workers) beat single-agent Opus by 90.2% on an internal breadth-first eval, but at roughly 15x chat token cost, and its own appendix recommends subagents persist outputs to a filesystem and pass references back "to minimize the game of telephone". Cognition's counter-argument (shared context, no conflicting implicit decisions) holds for *generation* tasks, and LangChain independently confirmed it: parallel section-writing produced disjoint reports, so they restricted parallelism to the research phase and write the report in one shot. Context-rot evidence (Chroma, 18 models; "Lost in the Middle") shows degradation is a gradient that starts well below the window limit, is worsened by distractors and by semantically similar material, and is not fixed by bigger windows, which is the reason to keep workers' raw tool output out of the lead's context. Claude Code supports exactly this shape natively: isolated subagent contexts that return only a final report, per-subagent `model`/`tools`/`maxTurns`/`memory` frontmatter, plugin `agents/` directories, 20 concurrent subagents by default, three nesting layers, and a bundled `/deep-research` workflow that fans out, cross-checks and votes on claims. All three hypotheses survive, with amendments: (a) one subagent per *mutually exclusive* question, 3 to 5 by default, not one per question when questions overlap; (b) files on disk, yes, but with a short structured summary also returned in chat so the lead can decide on a second round; (c) a single merge schema, yes, and the schema should carry per-claim source URLs and explicit gaps so the synthesizer can drop unsourced claims.

## Questions and answers

### 1. When do parallel subagents beat a single long-context agent for research, and when do they hurt?

**Confidence: high** for the direction of the effect; **medium** for the exact breadth numbers (they come from Anthropic's internal eval and prompt heuristics, not an independent benchmark).

**When they win.** Anthropic's Research team reports that "multi-agent research systems excel especially for breadth-first queries that involve pursuing multiple independent directions simultaneously"; Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval" (example: enumerate board members of all IT S&P 500 companies). Their variance analysis on BrowseComp found token usage alone explains 80% of performance variance, with tool-call count and model choice explaining most of the rest, i.e. the win comes from spending more tokens in *separate* context windows [Anthropic multi-agent]. LangChain found the same thing independently: "single agent response quality suffers if the request has multiple sub-topics (e.g., compare A to B to C)" because one window must hold tool feedback for every topic, "context clash" appears, and a single agent "would naturally research each topic less deeply (# of search queries) before choosing to finish" [LangChain ODR blog]. Anthropic's context-engineering post generalises: a subagent "might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)" [Anthropic context engineering].

**When they hurt.** Cognition's "Don't build multi-agents" argues two principles: share full agent traces, not single messages, and "actions carry implicit decisions, and conflicting decisions carry bad results"; parallel subagents that cannot see each other produce inconsistent outputs (the Flappy Bird example), and in 2025 "running multiple agents in collaboration only results in fragile systems" [Cognition]. Anthropic concedes the same boundary: "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit... most coding tasks involve fewer truly parallelizable tasks than research" [Anthropic multi-agent]. LangChain's earlier version wrote report sections in parallel and "the reports were disjoint because the section-writing agents were not well coordinated", so they now "restrict multi-agent to research, and write the report in one-shot" [LangChain ODR blog]. Anthropic also notes current Claude Code subagents are synchronous: "the lead agent can't steer subagents, subagents can't coordinate" [Anthropic multi-agent].

**Measured failure modes.** The MAST study (1,642 traces, 7 frameworks, 41% to 86.7% failure rates) found the most common failure modes are step repetition (15.7%), reasoning-action mismatch (13.2%), not recognising completion (12.4%), disobeying task specification (11.8%), incorrect verification (9.1%) and no/incomplete verification (8.2%); context loss was 2.8%, information withholding 0.85%. Adding a high-level task-objective verification step to ChatDev gave +15.6% task success [MAST]. Anthropic saw the matching symptoms in practice: early agents "spawning 50 subagents for simple queries", subagents that "duplicate work, leave gaps, or fail to find necessary information" when the brief was vague ("research the semiconductor shortage" led two of three subagents to run the same searches) [Anthropic multi-agent].

### 2. How should subagent results be merged, and what do working systems actually do?

**Confidence: high.** Every working system does the same two things: the worker compresses its own trace into a cited summary before returning, and a *single* writer produces the final document from all summaries.

- **Anthropic Research**: subagents return findings to the LeadResearcher, which synthesizes and decides whether to spawn more; then a separate CitationAgent "processes the documents and research report to identify specific locations for citations". Appendix: "Subagent output to a filesystem to minimize the 'game of telephone'... Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator. This prevents information loss during multi-stage processing and reduces token overhead" [Anthropic multi-agent].
- **Anthropic deep-research skill (installed locally)**: coordinator never researches or reads worker notes; each researcher writes `research_notes/{title}/{topic}.md` with a fixed schema per key question (Takeaway, Cited Findings with `- claim — [Source](URL)`, Inferences, Gaps); a single report-writer subagent reads the folder and writes `reports/{title}.md`; the writer is told "If a research note contains a specific major finding... without an inline source URL, do not include it" [deep-research SKILL.md, researcher.md, report-writer.md].
- **open_deep_research**: each researcher ends with a `compress_research` node using a separate `compression_model` that must preserve all relevant statements and inline citations with sequential numbering; the supervisor sees only `compressed_research`; `final_report_generation` concatenates all notes plus the brief into one model call [DeepWiki ODR, LangChain ODR blog].
- **gpt-researcher deep mode**: recursive tree returns `learnings`, `visited_urls`, `citations`, `context`; `trim_context_to_word_limit` keeps the most recent items under `MAX_CONTEXT_WORDS`; a fresh `GPTResearcher(DetailedReport)` writes from the aggregated context [DeepWiki GPTR].
- **STORM**: parallel persona conversations feed a `StormInformationTable`; outline is generated once from concatenated dialogue; each section is written from top-k retrieved snippets with `[n]` citations; `StormArticle.reference` maps URL to a unified citation index [DeepWiki STORM].
- **deer-flow**: subagents return structured results through `task()`; a Reporter aggregates; inline `[citation:TITLE](URL)` is mandatory and a Sources section closes the report; `knowledge_sources` snapshots pair a citation id with the exact excerpt [DeepWiki deer-flow].
- **Claude Code workflows**: `agent()` accepts a JSON `schema`; the subagent returns validated JSON (up to five validation retries) and intermediate results live in script variables, not Claude's context; `/deep-research` "votes on each claim" and filters claims that fail cross-checking, listing unverifiable claims as unverified [CC workflows].

Shared memory between workers is used by none of these for research; agent teams (shared task list, peer messaging) are the Claude Code primitive for it, and the docs say they "use significantly more tokens" and fit cases where teammates "challenge each other's findings" [CC agent-teams]. Cognition's position is that this peer-coordination is exactly what is fragile today [Cognition].

### 3. How do Claude Code subagents work specifically?

**Confidence: high** (official docs, opened 2026-10-16).

- **Context isolation**: each subagent "starts with a fresh, isolated context window"; it gets its own system prompt plus environment details, the delegation message, CLAUDE.md hierarchy (unless `omitClaudeMd: true`; Explore and Plan skip it), a git status snapshot, preloaded skills, and a sibling roster; it does not see the parent's history, invoked skills or files read. Forks are the exception. Context window size is set by the subagent's own model, and compaction "triggers as the subagent's own context window fills" (`autoCompactWindow` 100000-1000000, v2.1.296+) [CC sub-agents].
- **What returns**: "returns only the summary"; the final report arrives under a header marking it as subagent output, scanned for instruction-shaped text; a background subagent's report arrives as a completion notification in a later turn; Claude receives the agent ID. Transcripts persist at `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl` for `cleanupPeriodDays` (30 default) [CC sub-agents].
- **Tool restrictions**: `tools` allowlist or `disallowedTools`; subagents inherit built-in and MCP tools of the parent, minus `Agent` at the depth limit and `ExitPlanMode`; background subagents keep every MCP tool but only a fixed built-in set (Read, Grep, Glob, LSP, Bash, Edit, Write, WebFetch, WebSearch, TodoWrite, Skill, ToolSearch, ...). `Agent(worker, researcher)` syntax restricts which subagent types a main-thread agent may spawn [CC sub-agents].
- **Model selection**: `model: sonnet|opus|haiku|fable|<full id>|inherit`; per-invocation `model` and `effort` parameters override and persist across resume; `CLAUDE_CODE_SUBAGENT_MODEL` (+ `_FORCE`) runs every subagent on one model; the built-in Explore runs on the main model (Opus when main is Fable on Anthropic API) and can be overridden by defining a project `Explore` with `model: haiku` [CC sub-agents].
- **Resuming**: each invocation is a new instance; Claude resumes via `SendMessage` to the agent ID/name and the subagent keeps its full history; `maxTurns` exhaustion returns output "marked as partial" and resumable; Explore/Plan are one-shot; resumes take a concurrency slot without checking the limit [CC sub-agents].
- **Limits**: 20 concurrent subagents by default (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), no total cap; nesting three layers by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`); warning when custom subagent descriptions exceed 15,000 tokens; each subagent's requests count against the same usage limits [CC sub-agents, CC costs].
- **Memory**: `memory: user|project|local` gives the subagent its own `MEMORY.md` under `~/.claude/agent-memory/<name>/`, `.claude/agent-memory/<name>/` or `.claude/agent-memory-local/<name>/`; first 200 lines or 25KB are injected; `project` is the recommended scope; disabled if auto memory is off [CC sub-agents, CC memory].
- **Plugin placement**: `agents/` at plugin root (not inside `.claude-plugin/`); plugin subagents are namespaced `plugin:name`, have lowest precedence (5) after managed, `--agents`, `.claude/agents/`, `~/.claude/agents/`, and **ignore `hooks`, `mcpServers` and `permissionMode` frontmatter** for security; skills go in `skills/<name>/SKILL.md`; workflows in `workflows/`; a plugin `settings.json` can set `agent` to make a plugin agent the main thread [CC plugins, CC plugins-reference, CC sub-agents, CC workflows].
- **Built-in deep research**: `/deep-research` is a bundled *dynamic workflow*, not a subagent: it "fans out web searches on a question across several angles, fetches and cross-checks the sources it finds, votes on each claim, and returns a cited report with claims that didn't survive cross-checking filtered out"; requires WebSearch; runs in the background; intermediate results stay in script variables; 16 concurrent agents default, `Large workflow` warning above 25 agents or 1.5M projected tokens; resumable with saved per-agent results; agents in a fan-out share a prompt-cache prefix (held up to 5 s) [CC workflows, CC agents].
- **Compaction in the main session**: `/compact` replaces history with a summary; CLAUDE.md, auto memory and plan are re-injected from disk; up to five recently modified files re-read (files over 5,000 tokens come back as path references); invoked skill bodies re-injected capped at 5,000 tokens each and 25,000 total; background subagents keep running [CC context-window].

### 4. What does measured evidence say about context rot, and which mitigations work?

**Confidence: high** on the phenomenon; **medium** on the size of the effect for current Claude models (Chroma tested Claude 4-era models; no public re-run on Fable/Opus 5 was found).

- **Chroma "Context Rot" (18 models incl. Claude 4, GPT-4.1, Gemini 2.5, Qwen3; 8 input lengths x 11 positions)**: "model performance consistently degrades with increasing input length" even when task difficulty is held constant; lower needle-question semantic similarity steepens the decline; "even a single distractor reduces performance", four compound it; haystacks that *preserve* logical flow hurt more than shuffled ones across all 18 models; LongMemEval full inputs (~113k tokens) scored "significantly" below focused inputs (~300 tokens) for every model, with Claude Sonnet 4 / Opus 4 showing the widest gap because they abstain under ambiguity rather than hallucinate [Chroma].
- **"Lost in the Middle" (Liu et al.)**: U-shaped curve, best at the start (primacy) and end (recency); GPT-3.5-Turbo in 20- and 30-document settings fell *below* closed-book (56.1%) when the answer was in the middle; extended-context variants (16K, 100K) performed the same as base models at equal input; going from 20 to 50 retrieved documents improved QA only ~1.5% (GPT-3.5) and ~1% (Claude 1.3), while retriever recall kept rising [Lost in the Middle].
- **Anthropic's framing**: context is a "finite resource with diminishing marginal returns"; attention is n² and training data skews short, so this is "a performance gradient rather than a hard cliff"; mitigations in order of weight: compaction (Claude Code keeps architectural decisions and unresolved bugs, discards redundant tool outputs; "tool result clearing" is the safest form), structured note-taking (NOTES.md, memory tool), and sub-agent architectures; "just in time" retrieval via lightweight identifiers (file paths, links) beats pre-loading; the lead saves its plan to memory because "if the context window exceeds 200,000 tokens it will be truncated" [Anthropic context engineering, Anthropic multi-agent].
- **Tool-side mitigations**: Claude Code caps tool responses at 25,000 tokens by default; tools should paginate/filter/truncate and return natural-language identifiers rather than UUIDs; MCP tool definitions are deferred until used [Anthropic writing tools, CC costs].
- **Cognition's mitigation**: a dedicated compression model (they fine-tuned a small one) that condenses "a history of actions & conversation into key details, events, and decisions"; still hits a limit eventually [Cognition].

Implication for *this* plugin: a research question's raw material (fetched pages, DeepWiki answers, search results) is exactly the distractor-rich, semantically-similar content Chroma shows is worst, so it must never accumulate in the lead's window.

### 5. Model choice per role, and what Anthropic recommends for orchestrator-worker patterns

**Confidence: medium-high.** Anthropic's production data point is Opus lead + Sonnet workers; Claude Code docs recommend Sonnet for teammates and Haiku for "simple subagent tasks".

- Anthropic Research shipped Claude Opus 4 as lead and Claude Sonnet 4 as subagents; "upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7", so worker model quality matters more than worker token budget [Anthropic multi-agent].
- Anthropic's routing guidance: send easy/common work to Haiku and hard/unusual work to Sonnet; orchestrator-workers fits "search tasks that involve gathering and analyzing information from multiple sources"; evaluator-optimizer fits "complex search tasks that require multiple rounds... where the evaluator decides whether further searches are warranted"; start with "the simplest solution possible" [Anthropic building agents].
- open_deep_research separates four model roles: summarization (cheapest, `gpt-4.1-mini`), research, compression, final report; their Deep Research Bench runs show research-model upgrades moving the RACE score (0.4309 defaults vs 0.4943 with GPT-5) at large token cost, and Claude Sonnet 4 as researcher cost $187 vs $46 for defaults for a 0.44 vs 0.43 score [LangChain ODR README via Exa, DeepWiki ODR].
- Claude Code: "Use Sonnet for teammates", "For simple subagent tasks, specify `model: haiku`", reserve Opus for architectural decisions; per-subagent `effort` can lower thinking cost; prompt cache is shared across fan-out siblings with identical model/effort/tools/schema, so keeping workers homogeneous saves cache writes [CC costs, CC workflows].
- Anthropic's lead-agent prompting advice: use extended thinking as the planning scratchpad; teach the orchestrator to give each subagent "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; embed effort-scaling rules; "start wide, then narrow"; evaluate with a single LLM-judge call scoring factual accuracy, citation accuracy, completeness, source quality and tool efficiency [Anthropic multi-agent].

## Implications for the researcher plugin

**Recommended architecture: "bounded fan-out, file notes, single synthesizer, verifier pass".**

1. **Lead (coordinator) skill, not a long-running research agent.** A `skills/research/SKILL.md` that decomposes the brief into 1-5 mutually exclusive sub-questions using the deep-research table, writes the brief and plan to `research/runs/<slug>/PLAN.md` first (Anthropic's plan-to-memory rule), spawns workers in one turn, reads only their short returned summaries, and runs at most one gap-filling round. The lead never fetches pages itself. Model: the session model (Opus/Fable class); effort high. EARS: *When a brief has more than one independent facet, the lead shall spawn one worker per facet and shall not fetch sources itself.*
2. **Worker subagent definition in `agents/researcher.md`.** Frontmatter: `tools` limited to Read, Write, Grep, Glob, WebFetch, WebSearch plus the research MCP tools (Exa, DeepWiki, Context7, Playwright); `model: sonnet` by default with per-invocation override to the lead's model for hard sources; `maxTurns` around 40 (one tool call per turn, matching the 10-15 call budget with headroom); `omitClaudeMd: true` so the worker takes everything from the delegation prompt; `memory: project` so repeated tool verdicts (e.g. "DeepWiki has no index for repo X") persist in `.claude/agent-memory/researcher/`. Remember plugin agents cannot set `hooks`, `mcpServers` or `permissionMode`.
3. **Workers write a fixed-schema note to disk and return a 10-line summary.** Hypothesis (b) is confirmed but amended: both channels are needed. The file is the source of truth for the synthesizer; the chat return (takeaways, gaps, confidence, path) is what lets the lead decide on a second round without re-reading. Schema per key question: Takeaway, Cited findings (`claim — URL, date opened, tool`), Contradictions, Inferences, Gaps, Tools evaluated row. This matches `_FORMAT.md` and the deep-research researcher schema. EARS: *When a worker finishes, it shall write its note to the assigned path and return only takeaways, gaps and the path.*
4. **One synthesizer subagent writes the merged findings file.** It reads the notes folder, drops any claim without a URL, flags contradictions, and emits the `_FORMAT.md` sections. Never let workers write sections of the final document (LangChain's disjoint-report failure). Hypothesis (c) is confirmed: the merge format is the note schema plus `_FORMAT.md`.
5. **Add a verifier step for high-stakes claims.** MAST's largest avoidable category is weak verification (+15.6% from objective-level checks); Claude Code's `/deep-research` already votes on claims. Cheapest version: a `verifier` subagent (Haiku or Sonnet) that re-opens a sample of cited URLs and marks each claim verified/unverified; later, implement the whole pipeline as a `workflows/research.js` dynamic workflow so cross-checking and JSON `schema` returns are enforced by the runtime rather than by prompt.
6. **Context-rot controls.** Workers, not the lead, hold raw pages; `maxCharacters` on Exa fetches and WebFetch prompts keep per-call output small; the lead's `/compact` custom instruction preserves PLAN.md and the list of note paths; the tool registry row is written by the worker at the moment it opens a tool, so verdicts are not reconstructed from a rotted context.
7. **Effort scaling in the lead prompt.** Copy Anthropic's rule: single fact = 0 workers (lead answers via one tool call); comparison = 2-4 workers; landscape/enumeration = 5+; cap at 8 to stay well under the 20-concurrent limit and the 1.5M-token `Large workflow` warning.

**Alternatives rejected.**
- *Single long-context agent with compaction only*: rejected for multi-topic briefs because of the measured single-agent depth loss (LangChain), Chroma's distractor results, and the fact that research raw material is the worst kind of context. Keep it for one-fact questions.
- *One subagent per research question regardless of overlap (hypothesis (a) as stated)*: rejected; Anthropic's duplicated-semiconductor example shows overlapping briefs produce duplicate searches. Decompose into mutually exclusive facets first, then one worker per facet.
- *Agent teams with peer messaging*: rejected for now; docs say roughly 7x tokens, experimental and disabled by default, and Cognition's fragility argument applies. Revisit for "challenge each other's findings" review rounds.
- *Workers return everything in chat*: rejected; Anthropic's filesystem-artifact recommendation and the 1,000-2,000 token return budget.
- *Parallel writers for the final document*: rejected on LangChain's direct evidence.
- *Haiku workers by default*: not adopted; Anthropic's data says worker model quality beats token budget, and Haiku is reserved for the verifier and for trivially bounded tasks.

## Open questions

- No public benchmark re-runs Chroma's context-rot protocol on Fable, Opus 5 or Sonnet 5; the degradation slope for the models this plugin will actually run is unmeasured.
- Anthropic's 90.2% figure is an internal eval on breadth-first queries; there is no published number for *depth-first* tool-connection research (how two systems integrate), which is closer to this plugin's workload.
- Whether Claude Code's `/deep-research` workflow can be invoked from a plugin skill or only by the user; the docs state it "runs only when you invoke it".
- Whether `maxTurns` counts tool calls one-to-one (needed to map Anthropic's 10-15 call budget onto a turn cap).
- DeepWiki answers are wiki summaries, not source reads; config defaults quoted from it (e.g. `max_concurrent_research_units` 5) should be confirmed against the repos' `configuration.py` before being cited externally.
- Cost ceiling: at ~15x chat tokens per research run, how many runs per day fit the user's plan limits (see budget question in `research/open-questions.md`).
